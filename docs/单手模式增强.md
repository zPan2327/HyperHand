# 小米 14 / HyperOS 3 单手模式触发增强（HyperHand）

> 设备：Xiaomi 14（houji，23127PN0CC） · HyperOS 3 `OS3.0.305.0.WNCCNXM` · Android 16 (SDK 36)
> 环境：KernelSU + Zygisk（NeoZygisk）+ Vector 2.2.1（实现 libxposed API 102）
> 结论：**只改触发层**，缩小动画 / 缩小布局 / 触摸映射 / 退出方式 100% 沿用原生。

### 1.2 手势导航下"下滑进入单手模式"的真实调用链

```
触摸落在屏幕底部 76px（25dp）
  → com.miui.home (桌面进程) 的 NavStubView（GestureStubHome 窗口）
  → NavStubView.isStartOrStopOneHandMode()
       条件: isOneHandedModeEnabled() && (initY - currY) < -mOneHandedTouchSlop(=4px)   // 即下滑超过 4px
  → NavStubView.oneHandTouchResolution()  (ACTION_UP)
  → OneHandedModeInputConsumer.startOrStopOneHandMode(ctx, currY, downY)
       条件: 未激活 && (currY - downY) > 0  → MiuiSystemUiProxyWrapper.startOneHandedMode()
  → SystemUI 进程 WMShell: OneHandedController.startOneHanded()
  → OneHandedDisplayAreaOrganizer.scheduleOffset(0, height * config_one_handed_offset(0.4))
  → 原生缩小动画 / 下半屏布局
退出（原生，全部保留）:
  OneHandedTouchHandler：点击缩小区域上方 → onStop()；时长超时 → stopOneHanded()
  NavStubView：单手模式激活时胶囊条上滑 → stopOneHandedMode()
```

**核心结论 1：随手势导航，入口手势不在 SystemUI，而在桌面（`com.miui.home`）的 `NavStubView`。**

**核心结论 2：触发区就是 `NavStubView.getHotSpaceHeight()` 返回的高度，硬编码 25dp（隐藏提示线时 20.5dp）；本机实测 = 76px。**
代码（`NavStubView.java:6751`）：

```java
public int getHotSpaceHeight() {
    float f = 25.0f;
    if (!DeviceConfigs.IS_FOLD_DEVICE_WITH_SHELL && this.mHideGestureLine) f = 20.5f;
    return (int) (f * getResources().getDisplayMetrics().density);   // 25dp * 3.04 ≈ 76px
}
```

所以"手感差"的根因不是阈值太严（下滑 4px 就判定，已经很小），而是**可落指的区域只有屏幕最底部 76px**：
手指稍微高一点（例如离底 100px），事件根本进不了 `NavStubView`，直接被 App 收走。

其它已确认的判定细节（供参考，本次未改）：

- `TOUCH_SLOP = 8px`（`NavStubView` 静态字段），用于普通上滑/横滑起步判定；
- `mOneHandedTouchSlop = 4`（构造函数里赋值），用于单手模式方向判定；
- 横向为主（`|dy|*2 < |dx|` 且 `|dx| > 8px`）时走"横滑透传"分支，不会误判为单手；
- 横屏 / 隐藏提示线（`hide_gesture_line=1`）/ 分屏时 `isStartOrStopOneHandMode()` 直接返回 false；
- `NavStubView.onComputeInternalInsets()` 会在 `mHideGestureLine`、`mIsShowNavBar`、空区域标记等情况下把 touchable region 置空。

### 1.3 冲突的真正来源：桌面自己的"下拉打开通知/控制中心"

扩大触发区之后，底部 56~70dp 这段区域会同时被两套逻辑盯上。实测（本机 `dumpsys` + 反编译 + logcat 三方对齐）链路如下：

```
手指在桌面区域（y < 2594，即胶囊条窗口之外）按下并下滑
  → com.miui.home 的 DragLayer 收到事件
  → StatusBarSwipeController.onControllerInterceptTouchEvent()
        canInterceptTouch(): 非锁屏/非布局预览/y <= DeviceConfigs.getScreenHeight()
        onControllerTouchEvent(): dy > mTouchSlop(= getScaledTouchSlop()*2 ≈ 16dp) 且 |dy| > |dx| 且单指
  → dispatchTouchToStatusBar(): 把整段 MotionEvent 逐帧转发到 SystemUI（后台线程）
  → binder: ISystemUiProxy.onStatusBarMotionEvent()  (transaction code 10)
  → SystemUI: LauncherProxyService$1.onTransact() case 10
  → MiuiShadeTouchHandlerImpl.handleExternalTouch()
       ├ 通知中心分支: ShadeViewController.startInputFocusTransfer() / finishInputFocusTransfer(vy)
       └ 控制中心分支: ControlCenterEventHandlerImpl.handleExpandEvent(ev, "overview_proxy")
```

两个关键结论：

1. 桌面下拉的判定阈值只有 **≈16dp**，比我们"4dp 起判"晚，但比"整段手势结束"早得多；一旦它接管，通知中心会在你手指还没抬起时就开始跟手展开，视觉上就盖过了单手模式。
2. 胶囊条窗口（`GestureStubHome`，y≥2594）是独立 window，触摸不会落到桌面根视图，所以**原生 25dp 区域不存在这个冲突**；冲突只发生在"我们新扩出来的那一段"。

## 二、阶段 2：技术方案比较

| 方案 | 可行性 | 侵入性 | 问题 |
|---|---|---|---|
| **A. 系统设置 / 资源覆盖（RRO）** | ❌ | 低 | 触发区高度是 `getHotSpaceHeight()` 里的**代码常量 25.0f**，不是资源，RRO 改不了；`settings` 里也没有对应开关。 |
| **B. LSPosed 钩子（本次采用）** | ✅ | 低，可随时停用 | 需要 LSPosed/Vector；本机 Vector 2.2.1 同时支持libxposed 现代 API 与 libxposed API。 |
| **C. KernelSU 模块替换系统组件** | ⚠️ | 高 | KernelSU 只做文件层 overlay，没有 Java 钩子能力；要改就得替换 `MiuiHome.apk`（体积 28MB、签名校验、OTA 冲突），风险与维护成本都高。 |
| **D. 自行实现一套手势** | ❌ 不采用 | 高 | 会与原生手势冲突，且必须自己重做缩小动画/触摸映射，违背"保留原生"的要求。 |

选型：**B**。KernelSU 在本方案中只作为 Zygisk/Vector 的宿主，不参与改动。

### 为什么不用"直接加高胶囊条窗口"

那是本模块里的**备选路径**（默认关闭）。它确实能扩大原生手势区，但 `NavStubView` 内部对"非手势触摸"的透传逻辑是：

- 快速点击（<300ms）→ UP 时 `injectEvent()` 把 DOWN/UP 注入给 App，**能点到**；
- 长按（>300ms 未移动）→ 只 `clearDownEvent()` 丢弃，**App 收不到长按**。

窗口只有 25dp 时没人会去那儿长按，所以原生没问题；一旦加高到 40~60dp，就会开始吞掉底部内容的长按（例如底部 Tab 长按菜单）。因此默认不启用，改走下面的"旁路监视器"方案。

## 三、阶段 3：实现

### 3.1 设计

单手模式启用时，SystemUI 里本来就常驻一条**手势监视器**通道：

```
OneHandedTouchHandler.updateIsEnabled()
  → InputManagerGlobal.monitorGestureInput("onehanded-touch", 0)
  → EventReceiver.onInputEvent() → OneHandedTouchHandler.onInputEvent(MotionEvent)
```

monitor 通道的语义是**只观察、不消费**：它能看到全屏所有触摸，但不影响事件分发。于是：

1. 在这条通道上做一次"底部下滑"判定（区域、方向、距离、速度、时长、冷却全部可配）；
2. 命中后调用 `OneHandedController.startOneHanded()` —— **和原生胶囊条下滑调用的是同一个方法**；
3. 之后的一切（缩小动画、缩小布局、触摸映射、点击上方退出、上滑退出、超时退出、无障碍播报）都由系统自己完成。

因此：

- 触发区从 25dp 扩大到 56dp（可配），**不改变任何窗口的触摸分配**；
- 点击延迟、长按丢失、返回手势、上滑回桌面/最近任务 —— 全部不受影响；
- 模块被停用后，代码完全不执行，行为立刻回到原生。

### 3.1.1 意图判别：单手模式 vs 通知/控制中心（三道闸门）

同一个"底部下滑"动作，系统里有两套语义。模块用三道互相独立的闸门把两者分开，任何一道命中就足以避免打架：

| 闸门 | 做法 | 作用 |
|---|---|---|
| **① 区域归属**（`oh_tuner_claim_zone`，默认开） | 在**桌面进程**钩住 `StatusBarSwipeController.canInterceptTouch(MotionEvent)`：若 DOWN 落在底部 `zone_dp` 内，直接 `setResult(false)`，让桌面自己的下拉手势在触发区内"让位" | 从源头阻止桌面把这段手势转发给状态栏，**于是"底部下滑"只表示单手模式**；通知/控制中心仍可从触发区上方或顶部状态栏下拉 |
| **② 抬手判定 + 速度门限**（`oh_tuner_min_velocity_px_s`，默认 500） | 触发时机从"移动中"改到 `ACTION_UP`（与原生 `NavStubView` 一致），并按整段手势的**向下峰值速度**决定：`vpeak >= 阈值` 才触发 | 慢拖（≈100~300 px/s）永远不触发，快甩（实测 1100~2700 px/s）必定触发；同时避免"某一帧恰好没满足条件"导致的时灵时不灵 |
| **③ 下拉信号互斥**（`oh_tuner_shade_guard`，默认开） | 在 SystemUI 里监听三个"用户正在下拉通知/控制中心"的信号（见 §1.3 的链路），只要本次手势期间出现过，就放弃单手模式 | 兜底：万一桌面作用域没开、或用户从触发区上方起手并滑入底部，也不会出现"缩屏 + 通知中心"同时发生 |

速度判定用的是**相邻事件增量**（`(y[i]-y[i-1])/(t[i]-t[i-1])`，只取向下分量）再取整段最大值，所以"先慢后快"的甩动同样能识别；`min_velocity=0` 时退化为纯位移触发（旧行为）。

### 3.4 防误触 / 意图判别规则（内置，自上而下命中即返回）

- 必须从底部 `zone_dp` 区域内起手，且横向落在居中 `width_ratio` 范围内；
- 手指最终位移必须向下（`dy > 0`），横向偏移不超过 `|dx| > dy * max_slope`；
- 位移不足 `min_dy_dp`（默认 4dp）→ 不触发（防止把轻点当成手势）；
- **速度门限**：`min_velocity > 0` 时要求向下峰值速度 `>= min_velocity`，慢拖不触发；
- 本次手势期间出现过"下拉通知/控制中心"信号 → 让位给系统（`shade_guard`）；
- 冷却期内重复手势 → 忽略；
- 锁屏、单手模式已激活、单手模式未启用 → 不触发；
- 多指 → 放弃。

### 3.6 用法

- **单手模式**：在屏幕底部约 56dp（当前实机配到 70dp）范围内**快速往下甩**一下（默认要求峰值速度 ≥500 px/s，实测快甩 1100~2700 px/s），屏幕整体下移 —— 与原生单手模式完全一样；
- **慢拖不触发**：慢慢往下拖（约 100~300 px/s）不会进单手模式，方便在底部区域内滑动/滚动；
- **通知中心 / 控制中心**：在触发区**上方**（屏幕中部或更高的位置）下拉，或从顶部状态栏下拉，行为完全不变；
- 退出方式保持原生：点一下缩小区域上方，或在胶囊条上上滑，或等待超时；
- 想调参数：打开「单手模式增强」App 改数值 → 保存 → 立即生效（配置经 SystemUI 进程写入 `Settings.Global`，不需要 root、不需要重启）。
  - 觉得不够灵敏：把「触发最小速度」从 500 调到 300~400，或调到 0 完全关闭速度判定；
  - 觉得误触多：调到 800~1200；
  - 想让触发区更大：加大「触发区高度」；想恢复通知中心的底部下拉空间：关掉「底部区域优先单手模式」。

## 四、2.2 触发算法（Reachability 化）

2.1 的判定是"位移 ≥ 4dp 且向下峰值速度 ≥ 500px/s"，只有一个二值门。三个具体问题：

1. **过度依赖峰值**：峰值取自相邻两帧位移 / 时间差。120Hz 屏一帧 6~8ms，单帧位移常在 10px 以内，
   量化误差能把速度估到 ±1000px/s；偶发一帧跳变就会造出假峰值 → 误触。
2. **慢滑被完全排除**：`min_velocity=500px/s` 意味着人的自然下拉（80~150px/s）永远不触发，
   必须"甩"，与 iPhone Reachability 的手感相反。
3. **只有一个门限**：达标即触发、差一点就完全不响应，调参时体验是跳变的。

### 4.1 采样

```
ACTION_DOWN → begin()
ACTION_MOVE → 先灌 getHistoricalXxx(i)（0..getHistorySize()-1），再灌当前采样
ACTION_UP   → finish()
缓冲 192 点，满了隔点抽稀（保住 DOWN 原点，否则位移算错）
时间轴以 DOWN 为零点、float 存毫秒（float 存 uptimeMillis 绝对值会丢精度）
```

### 4.2 速度：滑动窗口

```
v(i) = (y[i] - y[k]) / (t[i] - t[k]) * 1000 / density     [dp/s]
k    = t[i]-t[k] <= velocity_window_ms 的最远采样（默认 60ms）
```

| 量 | 定义 | 用途 |
|---|---|---|
| `vpeak` | 所有窗口速度的最大值（只取向下分量） | 快甩路径 |
| `vavg` | 总位移 / 总时长 | 慢拉路径 |
| `v_end` | 抬手前最后一个窗口的速度 | 识别"拉下去又推回来" |
| `monotonic` | 净位移 / 路程（Y 方向） | 识别来回蹭 |

超过 `max_velocity`（默认 4000dp/s）按上限截断。

### 4.3 双路径评分

```
score(v, thr) = smoothstep(0.45*thr, thr, v)      // 达标满分，不足平滑衰减
confA = min(score(dy, min_dy),          score(vpeak, min_velocity), dir, stab)
confB = min(score(dy, slow_dy),         score(vavg,  min_avg_velocity), dir, stab)
conf  = max(confA, confB)  [+自适应] [×0.75 若抬手前已停住]
触发  ⇔ conf >= min_confidence
```

硬性闸门（命中即放弃，不参与评分）：方向向下、`|dx|/dy ≤ max_slope`、
`monotonic ≥ min_monotonic`、抬手前无反向、时长上限、互斥闸门、冷却、多指、横屏、锁屏。

三种模式的门限：

| 模式 | min_dy | min_velocity | slow_dy | min_avg_velocity | min_confidence |
|---|---|---|---|---|---|
| 0 自然 | 12dp | 60dp/s | 28dp | 35dp/s | 0.50 |
| 1 灵敏 | 8dp | 40dp/s | 20dp | 25dp/s | 0.42 |
| 2 防误触 | 18dp | 120dp/s | 44dp | 70dp/s | 0.60 |

## 五、2.4 遮罩外观：把米白换成模糊壁纸

### 5.1 先搞清"那块米白"到底是谁画的

不靠猜，全在真机上取证：

1. `dexdump` 读 `MiuiSystemUI.apk`（52MB，`/system_ext/priv-app/MiuiSystemUI/`），
   看 `com.android.wm.shell.onehanded` 包：
   - `OneHandedController` **没有** `startOneHanded`，只有 `stopOneHanded(int)` / `asOneHanded()`；
     启动逻辑在 `OneHandedController$OneHandedImpl.startOneHanded()`。
   - `BackgroundWindowManager` 有 `View mBackgroundView` + `SurfaceControlViewHost`，
     颜色来自 `getThemeColorForBackground()`，回调是 `showBackgroundLayer()/initView()/updateThemeOnly()`。
2. `dumpsys SurfaceFlinger` 里看到两层：
   - `BackgroundWindowManager#… → background-panel`：全屏，在最底层；
   - `one-handed-tutorial-overlay`：**只有上半屏**（1200×1068 / 2670）。
3. `dumpsys window windows` 确认后者是**真的 WindowManager 窗口**：
   `Window #4 Window{… u0 one-handed-tutorial-overlay}`，`type=2024`，不可触摸。
4. 红/绿探针（把两层分别涂成红、绿）截图：上半屏**全绿**、只在下沿露出红边
   → 屏幕看到的米白是 **`one-handed-tutorial-overlay`**，`background-panel` 只是它的垫底。

### 5.2 实现：两个入口，一个 drawable

```
BackgroundWindowManager.showBackgroundLayer() ─┐
                     .initView()              ─┼→ after → BlurBg.apply(this)
                     .updateThemeOnly()       ─┘

WindowManagerGlobal.addView(View, LayoutParams, …) ─→ after
        按 window title 匹配 "one-hand"/"onehand"
        → BlurBg.applyToOverlay(view, title)          （命中 one-handed-tutorial-overlay）

OneHandedTutorialHandler.fillBackgroundColor() ─┐
                        .updateThemeColor()    ─┼→ after → BlurBg.refreshOverlay()
                        .onAnimationUpdate()   ─┘        （同帧替换，避免闪烁）
```

要点：

- 窗口层用 `WindowManagerGlobal#addView` 按 **window title** 抓 View，不依赖 WMShell 私有字段名，
  换机型/换版本更耐操；`mBackgroundView` 那条路径仍然保留（它是垫底层）。
- **线程**：`background-panel` 的 ViewRootImpl 建在 `wmshell.main` 线程上，
  必须用 `view.post()` 投到它自己的 handler；直接在主线程 `setBackground` 会
  `CalledFromWrongThreadException: Expected: wmshell.main Calling: main`
  （这条是实测踩出来的，不是推测）。
- **闪烁**：系统会在入场过程中反复把遮罩刷回主题色。起初用 150ms 定时重贴 → 和系统重绘打架，肉眼可见闪。
  改为**钩住系统的"填色"回调，在同一帧里换成模糊图**，只在之后留 4 次稀疏补丁（260/620/1100/1800ms）。
- **不要黑边**：遮罩窗口只有上半屏高，而模糊位图是整屏比例。直接 FILL 会被纵向压扁，
  用 `gravity=FILL_HORIZONTAL|TOP` 在部分 window 上会留黑底。
  最终做法是按目标 View 尺寸从位图**顶端裁出同比例的一块**再 FILL（`cropTop()`，按高度缓存一张）。

生成流程（`BlurBg.build()`）：

```
WallpaperManager.getDrawable()        // SystemUI 持有 READ_WALLPAPER_INTERNAL
  → Canvas 按"铺满 + 居中"画到 1/6 分辨率（约 200×445）
  → 三遍盒式模糊（横向 + 纵向滑动窗口，O(n)），半径 = dp×density×缩放比
  → 按 blur_dim 压暗 RGB
  → 缓存，key = 壁纸 id | 屏幕尺寸 | 半径 | 压暗
```

`WallpaperManager#getBitmap()` 是 SystemApi（编译期拿不到），所以只用公开的 `getDrawable()`；
动态壁纸取不到位图时返回 null，保持系统米白，不做降级猜测。

### 5.3 顺带修掉的三个既有问题

1. **`startOneHanded()` 从来没真正调到。** 旧代码 `call(controller, "startOneHanded")`
   在 HyperOS 上必然抛 `NoSuchMethodException`，每次触发都静默走了
   "写 `one_handed_mode_activated=1`"的兜底。现在先 `asOneHanded()`，再扫描 `*OneHandedImpl`
   字段取实现对象调用；兜底保留。logcat 可见 `startOneHanded() via OneHandedController$OneHandedImpl`。
2. **配置接收器注册太晚。** 原本要等第一次触摸才注册，冷启动后第一次「保存」「预览」没反应。
   现在模块挂载后延迟 600ms 主动注册（Application 未就绪时会重试）。
3. **构建脚本撞 Windows 命令行长度上限。** 类文件变多后 `d8` 报"输入行太长"，
   改成先 `jar` 打包再交给 d8（`build.ps1` / `build.sh` 同步改）。
