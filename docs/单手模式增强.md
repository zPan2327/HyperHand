# 小米 14 / HyperOS 3 单手模式触发增强（HyperHand）

> 设备：Xiaomi 14（houji，23127PN0CC） · HyperOS 3 `OS3.0.305.0.WNCCNXM` · Android 16 (SDK 36)
> 环境：KernelSU + Zygisk（NeoZygisk）+ Vector 2.2.1（实现 libxposed API 102）
> 结论：**只改触发层**，缩小动画 / 缩小布局 / 触摸映射 / 退出方式 100% 沿用原生。

### 1.2 手势导航下"下滑进入单手模式"的真实调用链

```
触摸落在屏幕底部 76px（25dp）
  → com.miui.home (桌面进程) 的 NavStubView（GestureStubHome 窗口）
  → NavStubView.isStartOrStopOneHandMode()
       条件: isOneHandedModeEnabled() && (initY - currY) < -mOneHandedTouchSlop(=4px)   // 即下滑超过 4px
  → NavStubView.oneHandTouchResolution()  (ACTION_UP)
  → OneHandedModeInputConsumer.startOrStopOneHandMode(ctx, currY, downY)
       条件: 未激活 && (currY - downY) > 0  → MiuiSystemUiProxyWrapper.startOneHandedMode()
  → SystemUI 进程 WMShell: OneHandedController.startOneHanded()
  → OneHandedDisplayAreaOrganizer.scheduleOffset(0, height * config_one_handed_offset(0.4))
  → 原生缩小动画 / 下半屏布局
退出（原生，全部保留）:
  OneHandedTouchHandler：点击缩小区域上方 → onStop()；时长超时 → stopOneHanded()
  NavStubView：单手模式激活时胶囊条上滑 → stopOneHandedMode()
```

**核心结论 1：随手势导航，入口手势不在 SystemUI，而在桌面（`com.miui.home`）的 `NavStubView`。**

**核心结论 2：触发区就是 `NavStubView.getHotSpaceHeight()` 返回的高度，硬编码 25dp（隐藏提示线时 20.5dp）；本机实测 = 76px。**
代码（`NavStubView.java:6751`）：

```java
public int getHotSpaceHeight() {
    float f = 25.0f;
    if (!DeviceConfigs.IS_FOLD_DEVICE_WITH_SHELL && this.mHideGestureLine) f = 20.5f;
    return (int) (f * getResources().getDisplayMetrics().density);   // 25dp * 3.04 ≈ 76px
}
```

所以"手感差"的根因不是阈值太严（下滑 4px 就判定，已经很小），而是**可落指的区域只有屏幕最底部 76px**：
手指稍微高一点（例如离底 100px），事件根本进不了 `NavStubView`，直接被 App 收走。

其它已确认的判定细节（供参考，本次未改）：

- `TOUCH_SLOP = 8px`（`NavStubView` 静态字段），用于普通上滑/横滑起步判定；
- `mOneHandedTouchSlop = 4`（构造函数里赋值），用于单手模式方向判定；
- 横向为主（`|dy|*2 < |dx|` 且 `|dx| > 8px`）时走"横滑透传"分支，不会误判为单手；
- 横屏 / 隐藏提示线（`hide_gesture_line=1`）/ 分屏时 `isStartOrStopOneHandMode()` 直接返回 false；
- `NavStubView.onComputeInternalInsets()` 会在 `mHideGestureLine`、`mIsShowNavBar`、空区域标记等情况下把 touchable region 置空。

### 1.3 冲突的真正来源：桌面自己的"下拉打开通知/控制中心"

扩大触发区之后，底部 56~70dp 这段区域会同时被两套逻辑盯上。实测（本机 `dumpsys` + 反编译 + logcat 三方对齐）链路如下：

```
手指在桌面区域（y < 2594，即胶囊条窗口之外）按下并下滑
  → com.miui.home 的 DragLayer 收到事件
  → StatusBarSwipeController.onControllerInterceptTouchEvent()
        canInterceptTouch(): 非锁屏/非布局预览/y <= DeviceConfigs.getScreenHeight()
        onControllerTouchEvent(): dy > mTouchSlop(= getScaledTouchSlop()*2 ≈ 16dp) 且 |dy| > |dx| 且单指
  → dispatchTouchToStatusBar(): 把整段 MotionEvent 逐帧转发到 SystemUI（后台线程）
  → binder: ISystemUiProxy.onStatusBarMotionEvent()  (transaction code 10)
  → SystemUI: LauncherProxyService$1.onTransact() case 10
  → MiuiShadeTouchHandlerImpl.handleExternalTouch()
       ├ 通知中心分支: ShadeViewController.startInputFocusTransfer() / finishInputFocusTransfer(vy)
       └ 控制中心分支: ControlCenterEventHandlerImpl.handleExpandEvent(ev, "overview_proxy")
```

两个关键结论：

1. 桌面下拉的判定阈值只有 **≈16dp**，比我们"4dp 起判"晚，但比"整段手势结束"早得多；一旦它接管，通知中心会在你手指还没抬起时就开始跟手展开，视觉上就盖过了单手模式。
2. 胶囊条窗口（`GestureStubHome`，y≥2594）是独立 window，触摸不会落到桌面根视图，所以**原生 25dp 区域不存在这个冲突**；冲突只发生在"我们新扩出来的那一段"。

## 二、阶段 2：技术方案比较

| 方案 | 可行性 | 侵入性 | 问题 |
|---|---|---|---|
| **A. 系统设置 / 资源覆盖（RRO）** | ❌ | 低 | 触发区高度是 `getHotSpaceHeight()` 里的**代码常量 25.0f**，不是资源，RRO 改不了；`settings` 里也没有对应开关。 |
| **B. LSPosed 钩子（本次采用）** | ✅ | 低，可随时停用 | 需要 LSPosed/Vector；本机 Vector 2.2.1 同时支持libxposed 现代 API 与 libxposed API。 |
| **C. KernelSU 模块替换系统组件** | ⚠️ | 高 | KernelSU 只做文件层 overlay，没有 Java 钩子能力；要改就得替换 `MiuiHome.apk`（体积 28MB、签名校验、OTA 冲突），风险与维护成本都高。 |
| **D. 自行实现一套手势** | ❌ 不采用 | 高 | 会与原生手势冲突，且必须自己重做缩小动画/触摸映射，违背"保留原生"的要求。 |

选型：**B**。KernelSU 在本方案中只作为 Zygisk/Vector 的宿主，不参与改动。

### 为什么不用"直接加高胶囊条窗口"

那是本模块里的**备选路径**（默认关闭）。它确实能扩大原生手势区，但 `NavStubView` 内部对"非手势触摸"的透传逻辑是：

- 快速点击（<300ms）→ UP 时 `injectEvent()` 把 DOWN/UP 注入给 App，**能点到**；
- 长按（>300ms 未移动）→ 只 `clearDownEvent()` 丢弃，**App 收不到长按**。

窗口只有 25dp 时没人会去那儿长按，所以原生没问题；一旦加高到 40~60dp，就会开始吞掉底部内容的长按（例如底部 Tab 长按菜单）。因此默认不启用，改走下面的"旁路监视器"方案。

## 三、阶段 3：实现

### 3.1 设计

单手模式启用时，SystemUI 里本来就常驻一条**手势监视器**通道：

```
OneHandedTouchHandler.updateIsEnabled()
  → InputManagerGlobal.monitorGestureInput("onehanded-touch", 0)
  → EventReceiver.onInputEvent() → OneHandedTouchHandler.onInputEvent(MotionEvent)
```

monitor 通道的语义是**只观察、不消费**：它能看到全屏所有触摸，但不影响事件分发。于是：

1. 在这条通道上做一次"底部下滑"判定（区域、方向、距离、速度、时长、冷却全部可配）；
2. 命中后调用 `OneHandedController.startOneHanded()` —— **和原生胶囊条下滑调用的是同一个方法**；
3. 之后的一切（缩小动画、缩小布局、触摸映射、点击上方退出、上滑退出、超时退出、无障碍播报）都由系统自己完成。

因此：

- 触发区从 25dp 扩大到 56dp（可配），**不改变任何窗口的触摸分配**；
- 点击延迟、长按丢失、返回手势、上滑回桌面/最近任务 —— 全部不受影响；
- 模块被停用后，代码完全不执行，行为立刻回到原生。

### 3.1.1 意图判别：单手模式 vs 通知/控制中心（三道闸门）

同一个"底部下滑"动作，系统里有两套语义。模块用三道互相独立的闸门把两者分开，任何一道命中就足以避免打架：

| 闸门 | 做法 | 作用 |
|---|---|---|
| **① 区域归属**（`oh_tuner_claim_zone`，默认开） | 在**桌面进程**钩住 `StatusBarSwipeController.canInterceptTouch(MotionEvent)`：若 DOWN 落在底部 `zone_dp` 内，直接 `setResult(false)`，让桌面自己的下拉手势在触发区内"让位" | 从源头阻止桌面把这段手势转发给状态栏，**于是"底部下滑"只表示单手模式**；通知/控制中心仍可从触发区上方或顶部状态栏下拉 |
| **② 抬手判定 + 速度门限**（`oh_tuner_min_velocity_px_s`，默认 500） | 触发时机从"移动中"改到 `ACTION_UP`（与原生 `NavStubView` 一致），并按整段手势的**向下峰值速度**决定：`vpeak >= 阈值` 才触发 | 慢拖（≈100~300 px/s）永远不触发，快甩（实测 1100~2700 px/s）必定触发；同时避免"某一帧恰好没满足条件"导致的时灵时不灵 |
| **③ 下拉信号互斥**（`oh_tuner_shade_guard`，默认开） | 在 SystemUI 里监听三个"用户正在下拉通知/控制中心"的信号（见 §1.3 的链路），只要本次手势期间出现过，就放弃单手模式 | 兜底：万一桌面作用域没开、或用户从触发区上方起手并滑入底部，也不会出现"缩屏 + 通知中心"同时发生 |

速度判定用的是**相邻事件增量**（`(y[i]-y[i-1])/(t[i]-t[i-1])`，只取向下分量）再取整段最大值，所以"先慢后快"的甩动同样能识别；`min_velocity=0` 时退化为纯位移触发（旧行为）。

### 3.4 防误触 / 意图判别规则（内置，自上而下命中即返回）

- 必须从底部 `zone_dp` 区域内起手，且横向落在居中 `width_ratio` 范围内；
- 手指最终位移必须向下（`dy > 0`），横向偏移不超过 `|dx| > dy * max_slope`；
- 位移不足 `min_dy_dp`（默认 4dp）→ 不触发（防止把轻点当成手势）；
- **速度门限**：`min_velocity > 0` 时要求向下峰值速度 `>= min_velocity`，慢拖不触发；
- 本次手势期间出现过"下拉通知/控制中心"信号 → 让位给系统（`shade_guard`）；
- 冷却期内重复手势 → 忽略；
- 锁屏、单手模式已激活、单手模式未启用 → 不触发；
- 多指 → 放弃。

### 3.6 用法

- **单手模式**：在屏幕底部约 56dp（当前实机配到 70dp）范围内**快速往下甩**一下（默认要求峰值速度 ≥500 px/s，实测快甩 1100~2700 px/s），屏幕整体下移 —— 与原生单手模式完全一样；
- **慢拖不触发**：慢慢往下拖（约 100~300 px/s）不会进单手模式，方便在底部区域内滑动/滚动；
- **通知中心 / 控制中心**：在触发区**上方**（屏幕中部或更高的位置）下拉，或从顶部状态栏下拉，行为完全不变；
- 退出方式保持原生：点一下缩小区域上方，或在胶囊条上上滑，或等待超时；
- 想调参数：打开「单手模式增强」App 改数值 → 保存 → 立即生效（配置经 SystemUI 进程写入 `Settings.Global`，不需要 root、不需要重启）。
  - 觉得不够灵敏：把「触发最小速度」从 500 调到 300~400，或调到 0 完全关闭速度判定；
  - 觉得误触多：调到 800~1200；
  - 想让触发区更大：加大「触发区高度」；想恢复通知中心的底部下拉空间：关掉「底部区域优先单手模式」。

## 四、2.2 触发算法（Reachability 化）

2.1 的判定是"位移 ≥ 4dp 且向下峰值速度 ≥ 500px/s"，只有一个二值门。三个具体问题：

1. **过度依赖峰值**：峰值取自相邻两帧位移 / 时间差。120Hz 屏一帧 6~8ms，单帧位移常在 10px 以内，
   量化误差能把速度估到 ±1000px/s；偶发一帧跳变就会造出假峰值 → 误触。
2. **慢滑被完全排除**：`min_velocity=500px/s` 意味着人的自然下拉（80~150px/s）永远不触发，
   必须"甩"，与 iPhone Reachability 的手感相反。
3. **只有一个门限**：达标即触发、差一点就完全不响应，调参时体验是跳变的。

### 4.1 采样

```
ACTION_DOWN → begin()
ACTION_MOVE → 先灌 getHistoricalXxx(i)（0..getHistorySize()-1），再灌当前采样
ACTION_UP   → finish()
缓冲 192 点，满了隔点抽稀（保住 DOWN 原点，否则位移算错）
时间轴以 DOWN 为零点、float 存毫秒（float 存 uptimeMillis 绝对值会丢精度）
```

### 4.2 速度：滑动窗口

```
v(i) = (y[i] - y[k]) / (t[i] - t[k]) * 1000 / density     [dp/s]
k    = t[i]-t[k] <= velocity_window_ms 的最远采样（默认 60ms）
```

| 量 | 定义 | 用途 |
|---|---|---|
| `vpeak` | 所有窗口速度的最大值（只取向下分量） | 快甩路径 |
| `vavg` | 总位移 / 总时长 | 慢拉路径 |
| `v_end` | 抬手前最后一个窗口的速度 | 识别"拉下去又推回来" |
| `monotonic` | 净位移 / 路程（Y 方向） | 识别来回蹭 |

超过 `max_velocity`（默认 4000dp/s）按上限截断。

### 4.3 双路径评分

```
score(v, thr) = smoothstep(0.45*thr, thr, v)      // 达标满分，不足平滑衰减
confA = min(score(dy, min_dy),          score(vpeak, min_velocity), dir, stab)
confB = min(score(dy, slow_dy),         score(vavg,  min_avg_velocity), dir, stab)
conf  = max(confA, confB)  [+自适应] [×0.75 若抬手前已停住]
触发  ⇔ conf >= min_confidence
```

硬性闸门（命中即放弃，不参与评分）：方向向下、`|dx|/dy ≤ max_slope`、
`monotonic ≥ min_monotonic`、抬手前无反向、时长上限、互斥闸门、冷却、多指、横屏、锁屏。

三种模式的门限：

| 模式 | min_dy | min_velocity | slow_dy | min_avg_velocity | min_confidence |
|---|---|---|---|---|---|
| 0 自然 | 12dp | 60dp/s | 28dp | 35dp/s | 0.50 |
| 1 灵敏 | 8dp | 40dp/s | 20dp | 25dp/s | 0.42 |
| 2 防误触 | 18dp | 120dp/s | 44dp | 70dp/s | 0.60 |

## 五、2.4 遮罩外观：把米白换成模糊壁纸

### 5.1 先搞清"那块米白"到底是谁画的

不靠猜，全在真机上取证：

1. `dexdump` 读 `MiuiSystemUI.apk`（52MB，`/system_ext/priv-app/MiuiSystemUI/`），
   看 `com.android.wm.shell.onehanded` 包：
   - `OneHandedController` **没有** `startOneHanded`，只有 `stopOneHanded(int)` / `asOneHanded()`；
     启动逻辑在 `OneHandedController$OneHandedImpl.startOneHanded()`。
   - `BackgroundWindowManager` 有 `View mBackgroundView` + `SurfaceControlViewHost`，
     颜色来自 `getThemeColorForBackground()`，回调是 `showBackgroundLayer()/initView()/updateThemeOnly()`。
2. `dumpsys SurfaceFlinger` 里看到两层：
   - `BackgroundWindowManager#… → background-panel`：全屏，在最底层；
   - `one-handed-tutorial-overlay`：**只有上半屏**（1200×1068 / 2670）。
3. `dumpsys window windows` 确认后者是**真的 WindowManager 窗口**：
   `Window #4 Window{… u0 one-handed-tutorial-overlay}`，`type=2024`，不可触摸。
4. 红/绿探针（把两层分别涂成红、绿）截图：上半屏**全绿**、只在下沿露出红边
   → 屏幕看到的米白是 **`one-handed-tutorial-overlay`**，`background-panel` 只是它的垫底。

### 5.2 实现：两个入口，一个 drawable

```
BackgroundWindowManager.showBackgroundLayer() ─┐
                     .initView()              ─┼→ after → BlurBg.apply(this)
                     .updateThemeOnly()       ─┘

WindowManagerGlobal.addView(View, LayoutParams, …) ─→ after
        按 window title 匹配 "one-hand"/"onehand"
        → BlurBg.applyToOverlay(view, title)          （命中 one-handed-tutorial-overlay）

OneHandedTutorialHandler.fillBackgroundColor() ─┐
                        .updateThemeColor()    ─┼→ after → BlurBg.refreshOverlay()
                        .onAnimationUpdate()   ─┘        （同帧替换，避免闪烁）
```

要点：

- 窗口层用 `WindowManagerGlobal#addView` 按 **window title** 抓 View，不依赖 WMShell 私有字段名，
  换机型/换版本更耐操；`mBackgroundView` 那条路径仍然保留（它是垫底层）。
- **第一帧就要是模糊图**：在 `addView` 之后立刻贴一次。此时 View 还没量测，
  用 `LayoutParams` 里的 width/height 算裁切；连 LayoutParams 都是 `MATCH_PARENT(-1)` 时
  用 `Cfg.Screen`（`getRealMetrics`）的真实屏宽兜底。模块挂载后还会 `warmUp()` 预热位图缓存，
  所以连"装完模块后的第一次"也不会先露灰层。日志里 `bgBefore=null` 就表示我们在系统上色之前就贴好了。
- **尺寸一律运行时取**：代码里没有任何机型像素常量 ——
  View 尺寸取 `getWidth()/getHeight()` → 退 `LayoutParams` → 退 `getRealMetrics()`；
  模糊半径按 `dp × density` 折算；裁切比例由位图与目标 View 的宽高实时算。
  换分辨率/换刷新率/折叠屏都不需要改代码。
- **线程**：`background-panel` 的 ViewRootImpl 建在 `wmshell.main` 线程上，
  必须用 `view.post()` 投到它自己的 handler；直接在主线程 `setBackground` 会
  `CalledFromWrongThreadException: Expected: wmshell.main Calling: main`
  （这条是实测踩出来的，不是推测）。
- **闪烁**：系统会在入场过程中反复把遮罩刷回主题色。起初用 150ms 定时重贴 → 和系统重绘打架，肉眼可见闪。
  现在改为：`addView` 当场贴 + 钩住系统"填色"回调在同一帧替换 + 之后 4 次稀疏补丁
  （260/620/1100/1800ms，每次都先查重，不会重复贴）。
- **不要黑边/压扁**：遮罩窗口只有上半屏高，而模糊位图是整屏比例。直接 FILL 会被纵向压扁，
  用 `gravity=FILL_HORIZONTAL|TOP` 在部分 window 上会留黑底。
  最终做法是按目标 View 尺寸从位图**顶端裁出同比例的一块**再 FILL（`cropTop()`，按高度缓存一张）。

生成流程（`BlurBg.build()`）：

```
WallpaperManager.getDrawable()        // SystemUI 持有 READ_WALLPAPER_INTERNAL
  → Canvas 按"铺满 + 居中"画到 1/6 分辨率（约 200×445）
  → 三遍盒式模糊（横向 + 纵向滑动窗口，O(n)），半径 = dp×density×缩放比
  → 按 blur_dim 压暗 RGB
  → 缓存，key = 壁纸 id | 屏幕尺寸 | 半径 | 压暗
```

`WallpaperManager#getBitmap()` 是 SystemApi（编译期拿不到），所以只用公开的 `getDrawable()`；
动态壁纸取不到位图时返回 null，保持系统米白，不做降级猜测。

### 5.3 顺带修掉的三个既有问题

1. **`startOneHanded()` 从来没真正调到。** 旧代码 `call(controller, "startOneHanded")`


再对每帧按区域求平均色（`build-artifacts/Bands.java`）：
屏幕顶部 1~8%、8~20%、20~38% 三条带 + 全屏。**米白 `#DFDDE5` 的亮度是 223，模糊壁纸约 67**，
所以只要某帧顶部亮度跳到 200 以上，就是"灰了一下"，帧号即闪烁发生的时刻。

改造前的实测（2.4.6）：入场第 80 帧 `top=223`，前后都是 67 —— **恰好 1 帧**，
也就是 16ms 的灰，人眼就是"闪一下"。

### 6.2 三个真实原因

**① 我们贴图比窗口第一帧晚。**
`WindowManagerGlobal#addView` 之后原来的做法是 `view.post(...)` 投到该 View 的 handler，
实测要 **13~40ms** 才执行（两个刷新周期），而窗口第一帧早就画出来了 ——
那一两帧背景是空的，露出的就是垫底的米白。

**② 系统在入场动画里又把主题色刷回去。**
logcat 抓到关键一行：

```
blur bg applied: one-handed-tutorial-overlay ... bgBefore=null          # 我们贴上了
blur bg: blocked system repaint on overlay -> Color#FFDFDDE5            # 644ms 后系统要刷回米白
```

2.4.4 的做法是"系统刷回 → 我们 620ms 后再盖回去"，中间那几百毫秒就是灰；
而且反复重贴必然和系统重绘打架 → 表现为持续闪烁。

**③ 垫底层（`background-panel`）也会露出来。**
缩小动画刚开始的一两帧，overlay 还没合成上去，桌面已经缩小，中间露出的就是垫底的米白。
垫底层是 `BackgroundWindowManager.mBackgroundView`（本机是 `LinearLayout`，全屏 1200×2670），
它**只在第一次进入单手模式时才被创建**，所以在它建好之前没法预贴。

### 6.3 最终做法

| 问题 | 做法 |
|---|---|
| ① 贴图晚 | View **还没 attach** 时没有 ViewRootImpl，任何线程都能安全 `setBackground`，所以 `addView`/`setView` 之后**同步贴**，不再 post |
| ② 系统刷回 | 贴好即**上锁**：hook `View#setBackgroundDrawable`，凡是锁定的 View 上系统想设非本方 drawable，**直接跳过原方法**（日志记 `blocked system repaint`）。系统改不动，就没有"灰一下再变回来" |
| ③ 垫底层 | 用 `BackgroundWindowManager` 的 `mViewHost` 字段精确认领它的 View（不靠猜），同样贴图并上锁 |
| 兜底 | 仍保留 4 次稀疏补丁（260/620/1100/1800ms），只在锁失效的机型上才会真正生效；每次先查重 |

关键取舍：**不跟系统抢着重绘，而是让系统改不动**。
反复重贴是闪烁的根源；锁定之后重试只是保险，正常路径一次就完成。

关闭开关时会把两个 View 解锁并还原（垫底层还原主题色、overlay 交回系统下次重设），
不会停在模糊图上。

### 6.4 验证（真机，Xiaomi 14 / OS3.0.305.0.WNCCNXM）

2.5.0，连续两次"进入→退出→进入"，60fps 逐帧取色 429 帧：

| 检查项 | 结果 |
|---|---|
| 浅色帧（顶部亮度 > 150，即出现灰/白） | **0 帧**（2.4.6 时每次入场 1 帧、退出 1~2 帧） |
| 系统重绘拦截 | ✅ logcat：`blocked system repaint on overlay -> Color#FFDFDDE5` |
| 首帧即模糊 | ✅ 入场第一帧顶部亮度 67（= 模糊壁纸），无过渡灰 |
| 静止观感 | ✅ 上半屏模糊壁纸与下方桌面无缝、无黑边、无压扁 |
| 退出回桌面 | ✅ 退出段同样无浅色帧 |

> 说明：以上为广播触发（`oh_tuner_action=trigger`）测得的入场动画，与手势触发的
> `startOneHanded()` 是同一条路径。手势触发的人眼确认仍需用户手动下滑一次。

## 七、2.6 动画期间"应用上方先蒙一层灰"

2.5 之后不再闪了，但真实手势触发时还能看到：**缩小动画还没结束，上半屏就已经蒙了一层半透明灰**。
这次用 root 注入真实滑动（`input swipe` 到底部触发区）复现，逐帧取色 + 网格分区。

### 7.1 证据

关键帧（600×1334 录制，触发后第 337 帧，60fps）：

| 区域 | 触发前 | 该帧 | 结论 |
|---|---|---|---|
| 顶部 1~8%（8 列） | 128 111 85 75 70 79 90 81 | **103 88 76 67 64 60 58 50** | 整条被压暗 |
| 20~38% | 124 101 93 90 85 83 80 42 | **124 101 94 90 83 83 80 42** | 完全没动 |

即：**桌面还满屏（下半段数值没变），上半部分已经被压暗了**。
对照 `dumpTree` 的输出可以找到原因：

```
overlay tree(1) >>> FrameLayout[0x0] bg=BitmapDrawable a=0.0 vis=0
```

`one-handed-tutorial-overlay` 的 **alpha 从 0 淡入**，而它盖在应用**之上**；
里面装的就是我们贴的模糊图 → 动画还没开始时，它已经在应用上方以半透明形式出现了。
原厂遮罩是米白，同样会淡入，但因为颜色和"什么都没发生"接近，肉眼不容易察觉；
换成模糊图（暗灰）后这层半透明就很显眼。

### 7.2 做法：把模糊图从 overlay 挪到"垫底层"

| 层 | 位置 | 改法 |
|---|---|---|
| `background-panel`（`BackgroundWindowManager.mBackgroundView`） | 在应用窗口**之下** | 贴模糊图，并上锁 |
| `one-handed-tutorial-overlay` | 在应用窗口**之上** | **背景设为透明**（只保留它的提示文字/图标） |

这样：

- 动画开始前：overlay 是透明的，应用上方没有任何东西 → 不会提前蒙灰；
- 应用开始缩小：**它自己让出的缝里**才露出垫底层的模糊图，曝光量与动画同步；
- 稳定态：上半屏照样是模糊壁纸（因为垫底层就在下面）。

overlay 依然上锁（系统想把它刷成米白会被拦掉），只是锁的是一个"透明"状态。
另外留了兜底：若 400ms 后仍未抓到垫底层（个别机型），自动退回"overlay 自己贴模糊图"。

### 7.3 验证（真机，Xiaomi 14 / OS3.0.305.0.WNCCNXM）

| 项 | 方式 | 结果 |
|---|---|---|
| overlay 首帧透明 | `dumpTree`：`bg=BitmapDrawable a=0.0` → 改后不再贴图 | ✅ 日志无 `applied: one-handed-tutorial-overlay` |
| 垫底层出图 | `applied: background-panel ... bgBefore=Color#FFDFDDE5` | ✅ |
| 稳定态观感 | 截图 | ✅ 上半屏模糊壁纸，与下方无缝、无黑边 |
| 系统刷回米白 | `blocked system repaint on overlay` | ✅ 仍被拦下 |
| 动画期间应用上方无遮挡 | 逐帧：顶部条在应用未缩小前保持桌面数值 | ✅ 本次修复目标 |

> 遗留：动画最开始 1 帧，应用的**圆角**会先露一点点背景（系统缩放窗口时圆角先出现），
> 表现为左上/右上一个极小的深色角。这是窗口动画本身的形状，不是我们加的层；
> 若要彻底消除，只能改系统窗口动画，超出"只优化触发层"的范围。

## 8. 缩小 / 恢复动画：实测参数与调速（2.7）

### 8.1 调用链（dexdump `classes3.dex` 还原）

```
OneHandedController.startOneHanded()            // 入场
OneHandedController.stopOneHanded(int)          // 出场
  └─ OneHandedDisplayAreaOrganizer.scheduleOffset(dx, dy)
       └─ lambda$scheduleOffset$0 → animateWindows(token, leash, x, y, direction, mEnterExitAnimationDurationMs)
            └─ OneHandedAnimationController.getAnimator(...)
                 └─ setupOneHandedTransitionAnimator(animator)
                      • setSurfaceTransactionHelper / updateCornerRadius
                      • setInterpolator(new OneHandedInterpolator())
                      • setFloatValues({0f, 1f})
                 └─ setTransitionDirection / addCallback
                 └─ setDuration(mEnterExitAnimationDurationMs)
                 └─ start()
```

关键结论：**入场与出场走同一个 `animateWindows`，读同一个 `mEnterExitAnimationDurationMs`**，
所以不存在"入场快、出场慢"的差异，一处改动两边同时生效。

一次切换会起 **8 个 animator**（`mDisplayAreaTokenMap.forEach` 对每个 display area 各建一个），
它们在同一毫秒内 start，实测尾部结束时间相差 ≤ 16ms。

### 8.2 时长：600ms，且留了系统属性后门

`OneHandedDisplayAreaOrganizer` 构造器（dex 偏移 `0x2ab0be ~ 0x2ab0e0`）：

```java
mEnterExitAnimationDurationMs = SystemProperties.getInt(
        "persist.debug.one_handed_translate_animation_duration",
        context.getResources().getInteger(0x7f0c004a));
```

| 项 | 值 |
|---|---|
| 资源名 | `config_one_handed_translate_animation_duration`（`0x7f0c004a`） |
| 资源默认值 | **600**（aapt2 dump resources 读出） |
| 可覆盖属性 | `persist.debug.one_handed_translate_animation_duration` |
| 取值时机 | 构造时**一次性**读取，改属性必须重启 SystemUI |

> 这个后门是 AOSP 自带的调试口，模块不依赖它（要 root + 重启），
> 但可以作为"不改模块时先试试手感"的临时手段。

### 8.3 曲线：反汇编还原成公式

`OneHandedAnimationController$OneHandedInterpolator#getInterpolation(float)`（dex 偏移 `0x2a817c`）：

```
f(t) = 1 + 2^(-10t) · sin((t - 4) · π / 8)
```

即 Penner 的 ease-out expo 加正弦修正。采样值：

| t | 0.1 | 0.2 | 0.3 | 0.5 | 0.7 | 1.0 |
|---|---|---|---|---|---|---|
| 原生曲线 | **0.500** | **0.751** | **0.876** | 0.969 | 0.993 | 1.000 |

**前 10% 的时间就走完了一半位移，前 30% 走完 88%** —— 这就是"傻快"的来源：
问题不在 600ms 这个时长，而在这条曲线的头太陡。单纯把时长拉到 900ms，
只会变成"猛地冲到位、再定住 500ms"，更怪。

### 8.4 实测（给 animator 挂计时探针，uptimeMillis）

| 配置 | 请求时长 | 实测 start→end | 说明 |
|---|---|---|---|
| 原生（`×1.00` + 原生曲线） | 600ms | **614 ~ 626ms** | 差值 14~26ms 是首帧调度开销 |
| 放宽（`×1.10` + 柔和曲线） | 660ms | **674 ~ 691ms** | 同上，恒定的调度尾差 |

两次测量的差值（674−614 ≈ 60ms）与设定增量（660−600 = 60ms）完全吻合，
说明字段改写确实作用到了真正的动画上，而不是只改了一个没人读的变量。

### 8.5 做法：只改这一条动画

| 目标 | 手段 | 影响面 |
|---|---|---|
| 时长 | 反射写 `OneHandedDisplayAreaOrganizer.mEnterExitAnimationDurationMs` | 仅单手模式 |
| 曲线 | hook `setupOneHandedTransitionAnimator` 的返回值，替换 interpolator | 仅单手模式 |
| 不碰 | `ValueAnimator` 全局、窗口动画缩放、触摸映射、退出逻辑 | —— |

字段在构造器 after 里改写，首次读到的值记为"系统原始值"（`sSystemMs`），
之后无论怎么调都用 `系统原始值 × 倍率` 重算，**不会反复乘系数导致越调越慢**。

### 8.6 五条曲线

按"起步速度"从慢到快排，设置页里也是这个顺序，方便顺着试：

| 名称 | 公式 | t=0.1 | t=0.3 | t=0.5 | 手感 |
|---|---|---|---|---|---|
| 原生 | `1 + 2^(-10t)·sin((t-4)π/8)` | 0.500 | 0.876 | 0.969 | 一按就到位，后面干等 |
| 舒缓 | `3t² - 2t³` | 0.028 | 0.216 | 0.500 | 起手也减速，位移最均匀，但会"顿一下" |
| 柔和 | `1 - (1-t)³` | 0.271 | 0.657 | 0.875 | 中段近乎直线，**容易显得机械/线性** |
| 标准（默认） | `1 - (1-t)⁴` | 0.344 | 0.760 | 0.938 | 起步果断、尾部从容，有减速感又不冲 |
| 迅捷 | `1 - (1-t)⁵` | 0.410 | 0.830 | 0.969 | 最接近原生节奏，只是没那么极端 |

> 关于"线性"：ease-out cubic 的二阶导数在 t≈0.3 之后已经很小，
> 0.2~0.6 这段位移几乎是等速的（0.49 → 0.94），肉眼就会读成"匀速滑下去"。
> quart 把这段的斜率变化拉回来，同时保留了尾部的收束。
> 另外时长从 600ms 拉到 660ms 也会放大这种"匀速感"，所以曲线和时长要一起看。

### 8.7 设置项

- 位置：设置页「动画」分组
- 「缓动曲线」：原生 / 舒缓 / 柔和 / 标准 / 迅捷（默认「标准」）
- 「动画时长」：倍率 0.60 ~ 2.00（1.00 = 系统原生 600ms），步进 0.05
- **这两项改完即时生效**，不用点保存 —— 调手感本来就要来回试，
  每次保存再回桌面下滑太折腾；其它参数仍然走"保存并立即生效"。
- 卡片底部直接显示 SystemUI 回写的真实值：

```
系统原生 600ms · 曲线 ease-out expo（10% 时间 → 50% 位移）
当前 660ms（×1.10）· 标准
上次实测 676ms
```

改完点「保存并立即生效」即可，不需要重启进程（`AnimCtl.onConfigChanged` 会重写字段）。
（2.7.1 起这两项本身就是改动即时生效。）

## 9. 落点判定：拖到底才算单手模式（2.8）

### 9.1 问题

2.7 及以前只看"起点在底部 56dp 内 + 向下位移够 + 速度够"。这套条件在桌面上有个
绕不开的漏洞：**桌面抽屉、可滚动列表，手指也可能正好从底部 56dp 内起手往下拖 20dp**。
距离和速度都满足，于是抢走了本该交给页面的滚动。

单纯降门槛会让冲突更多，单纯抬门槛又会让单手模式变迟钝 —— 两个方向互相打架。

### 9.2 关键差别在终点

| | 起点 | 终点 |
|---|---|---|
| 单手模式 | 底部胶囊条附近 | **一路拖到屏幕最底边**（手指滑出屏幕，坐标被裁到底边） |
| 页面滚动 | 可能在底部区域 | 停在屏幕中段，不会贴到物理底边 |

所以新增一个判据：`endGapDp = (屏幕高度 - 抬手点 y) / density`。

- `endGapDp ≤ end_zone_dp`（默认 24dp）→ 认为"拖到底了"
- 否则 → 认为是页面滑动，**直接放行给应用**

### 9.3 两条路径的取舍

贴底本身是极强的意图信号，所以反过来可以放宽其它门槛：

| 判据 | 常规路径（2.7） | 贴底路径（2.8） |
|---|---|---|
| 向下位移 | ≥ min_dy（默认 12dp） | **≥ 6dp**（只挡点击） |
| 时长 | ≤ max_duration | **≥ 50ms**（只挡点击） |
| 峰值速度 | 必须达标 | **不看** |
| 平均速度 | 慢滑路径要求 | **不看** |
| 置信度 | ≥ 0.50 | **不看**（直接 1.0） |
| 单调性 / 横向 | 要求 | 要求（保留） |

结果就是：**想触发的时候更容易触发，不想触发的时候完全不抢**。
日志里贴底路径记为 `TRIGGER(E)`。

### 9.4 离线验证（`module/test/Test.java`）

```
=== 落点判定（2.8，贴底才算单手模式）===
T1 拖到底 20dp/200ms       dy= 20.0  end=  0.0  dur= 200  -> TRIGGER(E)
T2 贴底但只动 3dp          dy=  3.0  end=  3.6  dur=  60  -> SKIP(too_short)
T3 底部起手 10dp 未到底     dy= 10.0  end= 42.6  dur= 100  -> SKIP(not_at_bottom)
T4 底部起手上滑             dy=-30.0  end= 82.6  dur= 150  -> SKIP(not_downward)
T5 慢速拖到底 15dp/900ms    dy= 15.0  end=  0.0  dur= 900  -> TRIGGER(E)
T6 到底后停 300ms           dy= 20.0  end=  0.0  dur= 500  -> TRIGGER(E)
```

T3 是这次要解决的核心场景：起点在触发区、也确实向下拖了 10dp，但没到底 → 判给页面。
T5 说明贴底路径不再看速度，慢拖也能触发（灵敏度提升的来源）。

### 9.5 到边即触发（2.8.1）

初版是**等抬手**才判定，实机日志暴露了两个问题：

```
T 底部起手 10dp 未到底   dy=10.4dp  end=28.4dp  dur=158ms  -> SKIP(not_at_bottom)
```

1. 用户觉得自己"已经拖到底了"，实际抬手点离底边 28.4dp —— 24dp 的带宽差一点点没进；
2. 等 UP 才判，在可滚动页面上这 100~200ms 里内容已经跟着滚了一段，
   观感就是"既滚了页面又进了单手模式"。

改法：

- 带宽 24dp → **32dp**（给"我以为到底了"的主观误差留余量）；
- **MOVE 阶段到边即判**：手指一进入底边带子就立刻判定并触发，不等抬手，
  把那几十毫秒的滚动压到最短。提前判定失败时静默等下一帧，不写日志。

日志里提前触发的记录带 `early` 标记：

```
GESTURE mode=0 early dy=22.0dp dx=-2.4dp end=23.7dp dur=118ms ... -> TRIGGER(E)
```

### 9.6 实机数据的分布（2.8.0，一次会话 42 次底部触摸）

| 情况 | 次数 |
|---|---|
| 起点在触发区之外（页面中部滚动） | 22 |
| 起点在区内 → 触发 | 10 |
| 起点在区内 → 上滑，判定为滚动 | 9 |
| 起点在区内 → 向下但没到底 | 1 |

结论：**判定本身没问题，卡住触发的是"必须抬手才算"和 24dp 带宽太窄**。

### 9.7 桌面底部区域：通知/控制中心在区内彻底让位（2.8.2 → 2.8.3）

桌面往下拉会经过**两道**关卡，只卡住一道都不够：

```
① StatusBarSwipeController#canInterceptTouch(DOWN)   ← 决定"要不要接管这个手势"
        ↓ 接管
② DispatchTouchHandler.handleMessage()               ← 异步，把整段 MotionEvent
        ↓                                              直接交给下一环，不再回头问①
   SystemUiProxyWrapper#onStatusBarMotionEvent(MotionEvent)   [com.miui.home.recents]
        ↓ binder
   LauncherProxyService$1#onTransact(code=10)          [com.android.systemui]
        ↓
   通知中心 / 控制中心展开
```

2.8.2 只在 ① 让位、在 ④ 兜底吞掉。问题在于 ② 是 **Handler 异步派发**，
它拿到的是已经复制好的 MotionEvent，不会再问 ①，所以 ③ 照样会把事件发出去；
④ 再吞虽然能挡住展开，但这一段已经白跑了 binder，且 `shadeGuard` 时序上仍可能被点亮。

2.8.3 把拦截提到 ③，也就是**事件根本不出桌面进程**：

| 关卡 | 区内（起点距底 ≤ 58dp） | 区外 |
|---|---|---|
| ① `canInterceptTouch` | 返回 false，不接管 | 正常 |
| ③ `onStatusBarMotionEvent` | 返回 false，不转发 | 正常转发 |
| ④ `onTransact`（兜底） | 吞掉（万一还有别的路径） | 正常 |

"这次手势是不是从区内起手"记在桌面进程的 `sLauncherZoneDown` 里，
在 ① 收到 ACTION_DOWN 时按触发区几何（与 SystemUI 判定完全同一套，含宽度占比与左右偏置）写入，
转发结束（UP/CANCEL）时清掉，另有 2s 时间窗兜底，不会跨手势残留。

结果：

- **从底部 58dp 内往下拖** → 不展开通知/控制中心，拖到底就进单手模式；
- **从 58dp 之外的下拉** → 照常展开通知/控制中心，完全不受影响。

配套调整：

| 项 | 2.8.1 | 2.8.2 起 |
|---|---|---|
| 触发区高度 | 56dp | **72dp**（2.8.4 起，见 9.8） |
| 贴底路径最小位移 | 6dp | **4dp** |
| 贴底路径最短时长 | 50ms | **40ms** |

### 9.8 边界校准：58dp 切在了真实落点中间（2.8.4）

2.8.3 的拦截链路是通的（区内手势在 SystemUI 侧一条 `shade intent` 都没有），
但用户仍觉得"在底部拖还是弹通知中心"。原因在边界值本身。实机落点：

| 落点 y | 距底 | 58dp | 72dp |
|---|---|---|---|
| 2590 / 2553 / 2519 | 26 / 39 / 50dp | 区内 | 区内 |
| 2493 | **59dp** | 区外 → 弹通知中心 | 区内 |
| 2487 | **61dp** | 区外 → 弹通知中心 | 区内 |
| 2457 / 2437 | 71 / 78dp | 区外 → 弹通知中心 | 区内 |

用户的习惯落点集中在 **59~78dp**，58dp 的线正好切在中间：差的不是 1cm，是 1dp。

所以默认改成 **72dp**。这不是"扩大误触范围"，而是把边界从"用户落点中间"
挪到"用户落点之外" —— 屏幕中部（>80dp）的下拉依旧正常弹通知/控制中心。

设置页「触发区」卡片底部新增校准提示，直接用 SystemUI 实时数据：

```
最近一次起手：距底 61 dp · 区外
区线 72 dp · 超出区线 -11 dp，把高度调大约这个数
```

用法：回桌面按一下底部，切回设置页看这个数。显示"超出区线 xx dp"就把
「触发区高度」加大到"距底 + 10"；如果高度明明够却仍判区外，提示会变成
"问题在水平范围"，那时该看宽度占比和左右偏置。

后两项是"这个范围里再灵敏一点"的具体落点：既然 58dp 内的下拉已经不会被通知中心抢，
门槛就可以压到只剩"手指真的动了"。

### 9.8 设置项

- 「贴底才算单手模式」：默认开。关掉则回到 2.7 的纯速度/距离判定。
- 「贴底判定距离」：默认 32dp，范围 8~80dp。
  如果发现要很用力才触发（个别贴膜/手势区限制），把它调到 40~48dp 即可。

手势调试里每条记录都会带 `end=xx.x dp`，可以直接看抬手点离底边多远，
用来校准这个值。

## 10. 模糊区手势：下滑直接拉通知/控制中心（2.9）

### 10.1 问题

单手模式把界面缩小到下半屏后，状态栏也跟着搬到了缩小窗口的顶部
（本机 y=1068）。于是"下拉通知栏"这件事只能在那条线上完成 ——
手指必须精准地落在"虚拟顶部"，上半屏那么大一块模糊区完全没手势。

期望：上半屏随便哪往下滑，都能拉出通知中心/控制中心，并且**不用再手动退出单手模式**。

### 10.2 先搞清楚上半屏的触摸落在谁身上

`dumpsys window windows`（单手模式激活时）：

```
one-handed-tutorial-overlay  frame=[0,0][1200,1068]  touchableRegion=(0,0,1200,1068)
StatusBar                    frame=[0,1068][1200,1202]   ← "虚拟顶部"
NotificationShade            frame=[0,1068][1200,3738]
Launcher                     frame=[0,1068][1200,3738]
Embedded{background-panel}   frame=[0,0][1200,2670]
```

关键结论：

1. 所有 SystemUI 窗口都被**整体下移 1068px**（transform 里 `-1068`），
   这不是"缩小窗口"，而是"整个 UI 平移"；
2. 上半屏只有 `one-handed-tutorial-overlay` 可触摸，它就是模糊区，
   也是系统"点上方退出单手模式"的事件接收者；
3. 所以监听挂在它身上即可，**不需要自己算模糊区边界**，也不会干扰其它窗口的触摸分配。

### 10.3 做法

```
one-handed-tutorial-overlay (FrameLayout)
  └─ OnTouchListener（保留系统原有 listener，先调它再兜底）
       ACTION_DOWN  记录起点；非单手模式激活则完全不管
       ACTION_MOVE  dy ≥ 36dp 且 dx ≤ 1.6·dy  →  触发
       ACTION_UP    触发过就吞掉，避免系统再当"点击"退一次
```

触发后：

```
1. StatusBarManager.expandNotificationsPanel()   左半屏
   StatusBarManager.expandSettingsPanel(null)    右半屏
2. 等 120ms（面板动画起来）
3. OneHandedImpl.stopOneHanded()                 窗口在面板背后归位
```

**顺序不能反**。第一版是"先退出再展开"，日志里 `expanded via StatusBarManager` 明明成功，
截图却只剩干净桌面 —— 退出单手模式的流程会把刚展开的面板收掉。
反过来先展开、面板盖住屏幕，窗口归位的动画藏在后面，观感上就是"一下就拉下来了"；
用户收起面板时手机已经在正常模式里。

阈值 36dp 是"手指确实在往下拖"与"手滑一下"的分界；未达阈值时事件交回系统，
所以**点一下仍然是原生的"退出单手模式"**，没有破坏原有交互。

### 10.4 验证（真机，Xiaomi 14 / OS3.0.305.0.WNCCNXM）

用调试入口 `--es oh_tuner_action topshade`（不走手势，直接跑完整链路）：

```
TOP SHADE: swipe in blur area -> open notification center then exit one-handed (dy=36.0dp, x=600)
TOP SHADE: expanded via StatusBarManager
stopOneHanded() via OneHandedController$OneHandedImpl
```

截图确认：通知中心保持展开、背景已是归位后的模糊桌面；
`settings get secure one_handed_mode_activated` = 0。
改成"总是控制中心"（`oh_tuner_top_shade_side=2`）再跑一遍，
控制中心（亮度/音量滑块 + 快捷开关）同样正常展开且保留。

### 10.5 设置项

| 项 | 键 | 默认 |
|---|---|---|
| 下滑展开通知/控制中心 | `oh_tuner_top_shade` | 开 |
| 触发距离 | `oh_tuner_top_shade_dy_dp` | 36dp（8~80） |
| 拉开哪个 | `oh_tuner_top_shade_side` | `0` 左通知右控制（`1` 总是通知、`2` 总是控制） |

调试动作：`am broadcast -a io.github.zpan2327.hyperhand.action.SET -p com.android.systemui --es oh_tuner_action topshade`

### 10.6 统一退出逻辑：从哪儿拉出来的都要退出（2.9.1）

第一版只在模糊区手势里退出单手模式，于是出现不一致：

- 模糊区下滑 → 面板出来 **且** 退出单手模式 ✅
- 在"虚拟顶部"（缩小窗口顶部那条状态栏）下拉 → 面板出来，但**仍停在单手模式** ❌

这两条路径完全不同：前者是我们自己调 `expandNotificationsPanel()`，
后者是系统自己的 `StatusBar` 窗口在处理手势。所以补了三个入口，全部统一成
"面板被拉出来 → 120ms 后 `stopOneHanded()`"：

| 路径 | 判定点 | 做法 |
|---|---|---|
| 模糊区下滑 | `one-handed-tutorial-overlay` 的触摸，dy ≥ 36dp | 自己展开面板 + 120ms 后退出 |
| 虚拟顶部下拉（通知中心） | 手势监视通道：DOWN 落在 `[模糊区下沿, +状态栏高度+12dp]` 且抬手时下拉 ≥ 阈值 | 只退出，展开交给系统 |
| 虚拟顶部下拉（控制中心） | `ControlCenterEventHandlerImpl#handleExpandEvent` 的 **ACTION_UP** | 只退出，展开交给系统 |

三点设计取舍：

1. **只认抬手（UP）**：系统展开是跟着手指走的，拖动中途退出会让窗口带着面板一起上移，
   看起来像"面板被甩走了"。模糊区那条因为是自己一次性展开，才可以在 120ms 后退出。
2. **分界线用 `<` 不用 `<=`**：overlay 的 `touchableRegion` 是 `[0, 1068)`，
   `y == 1068` 已经属于状态栏，避免同一手势被两条路径同时接住。
3. **500ms 节流**：同一手势可能同时命中"状态栏带"和"控制中心处理器"，只执行一次。

状态栏带的高度不是写死的：`status_bar_height` 资源 + 12dp 余量，
拿不到才退化成 28dp。

### 10.7 手写手势判定不够用，改成挂"展开出口"（2.9.2 → 2.9.3）

2.9.1 上线后还剩两个坑：

**坑一：区域判断写成了每帧校验。** 原来是

```java
if (y > blurBottom + statusBarHeight) return;   // 每一帧都跑
```

DOWN 落在状态栏那条时 y≈1119（范围内，通过），但手指往下拖 300px 后，
UP 时 y 已经变成 1400+，直接被这行挡掉 —— "抬手退出"永远执行不到。
表现就是：右侧控制中心（走另一条钩子）能退，左侧通知中心（只走这条）不退。
改成**只在 ACTION_DOWN 判定一次归属**，后面 MOVE/UP 按归属走完。

**坑二：手写手势判定天生盖不全。** 面板可能在状态栏、应用内、锁屏、
快捷方式、程序化调用等各种地方被拉出来，逐个猜起点不现实。

于是改成挂**展开出口**：

| 面板 | 挂载点 | 说明 |
|---|---|---|
| 通知中心 | `NotificationPanelViewController#expand(Z)`、`expandToNotifications()`、`expandToQs()` | 三个方法就是面板唯一的展开出口（dexdump classes2.dex 确认），任何路径最终都落到这里 |
| 控制中心 | `ControlCenterImpl#expand(…)` | 控制中心本体的展开入口 |
| 控制中心（手势） | `ControlCenterEventHandlerImpl#handleExpandEvent` 的 ACTION_UP | 拖动式展开 |

配合原来的模糊区手势与状态栏带，现在"只要面板被拉出来就退出单手模式"。

**验证方式**（不需要手指，程序化展开也能覆盖到）：

```bash
adb shell cmd statusbar expand-notifications
adb shell cmd statusbar expand-settings
```

实测日志：

```
TOP SHADE: shade opened via notification_shade -> exit one-handed
stopOneHanded() via OneHandedController$OneHandedImpl
→ one_handed_mode_activated = 0，通知中心保持展开

TOP SHADE: shade opened via control_center -> exit one-handed
→ 控制中心保持展开
```

注意 120ms 的延迟仍然保留：立即 stop 会把面板收掉（和最初那个坑一样）。
模糊区那条会和 expand 钩子同时触发，两次 stop 都执行也无害。

### 10.8 屏幕中部（缩小窗口内容区）下拉也要退出（2.9.4）

2.9.3 之后还剩一处漏网：**在缩小窗口的中间内容区往下拉**。

单手模式下屏幕被切成三段：

```
y ∈ [0, 1068)      模糊区（overlay 自己接手势）
y ≈ 1068 ~ 1148    虚拟顶部（状态栏带）
y ∈ [1148, 2270)   缩小窗口的应用/桌面内容 ← 2.9.3 之后仍然漏
y ∈ [2270, 2670]   底部触发区（归单手模式）
```

在这块中间区域下拉时，事件由桌面/应用接住，再**转发**给 SystemUI 展开面板
（日志里的 `shade intent: launcher_forward`）。这条转发通道既没有"抬手"钩子可挂，
也不一定经过 `NotificationPanelViewController#expand`，所以面板出来了、
单手模式还在。日志证据：

```
16:09:40.010 DOWN outside zone x=932 y=1313   ← 中间区域起手
16:09:40.068 shade intent: launcher_forward    ← 面板确实开了
（没有任何 TOP SHADE 退出、没有 stopOneHanded）
```

修法：在手势监视通道里补一个归属 `MODE_APP`。

```
DOWN → y 在 (状态栏带底, 触发区顶) 之间，记 MODE_APP 和起手 y
MOVE → 不判定（拖动中退出会让窗口带着面板跳一下）
UP   → 位移 ≥ barPullPx(dp)
       且本次手势期间出现过 shade intent（HyperHand.lastShadeIntentAt()）
       → 退出单手模式
```

`shadeOpened` 这道条件很关键：没有它，在应用里正常往下滚一屏也会把单手模式退掉。

现在四条入口语义一致：

| 起手位置 | 归属 | 处理 |
|---|---|---|
| 模糊区 (y < 1068) | `MODE_BLUR` | 自己 expand + 延迟退出 |
| 虚拟顶部 (1068~1148) | `MODE_STRIP` | 交系统展开，抬手退出 |
| 内容区 (1148~2270) | `MODE_APP` | 交系统转发，抬手退出 |
| 底部触发区 (2270+) | 触发区 | 归单手模式，不拉面板 |

排查用日志（debug 开启时）：

```
TOP SHADE: shade opened via app_swipe -> exit one-handed
TOP SHADE: notification_shade ignored (not in one-handed)   ← 面板开了但已不在单手模式
TOP SHADE: control_center ignored (throttled)               ← 500ms 节流挡掉重复
TOP SHADE: app_swipe skip dy=42 need=30 shade=true          ← 位移不够，没当成下拉
```

### 10.9 "有时行有时不行"的两个真因（2.9.5）

日志（16:18 那一段）把失败分成了两类：

**真因一：刚进单手模式就下拉，激活位还没写进去。**

```
16:18:31.627  GESTURE ... -> TRIGGER(E)          ← 到边即触发，已开始进单手
16:18:32.208  shade intent: launcher_forward     ← 0.5s 后就下拉
16:18:32.287  TOP SHADE: control_center ignored (not in one-handed)
```

`startOneHanded()` 的状态写盘跟在窗口动画后面，实测有 0.3~0.8s 的空窗；
这期间 `one_handed_mode_activated` 还是 0，于是手柄判定"不在单手模式"，直接不算。
修法：`isOneHandedActive()` 加一道兜底 —— 距上次触发 1.8s 内一律按已激活处理
（`stopOneHanded()` 幂等，多认一次无害）。

**真因二：位移门槛按状态栏的 36dp 定的，内容区下拉大多到不了。**

面板是"跟手 + 抬手后惯性展开"的，用户常拖 40~80px 就松手；
而 `barPullPx` = 36dp × density ≈ 108px，于是被判成"没下拉"。
内容区改用独立的 `appPullPx` = **10dp**（只用来挡点击），
并且 MOVE 阶段就挂一个 400ms 兜底（面板展开时输入焦点会转移，有时收不到 UP）。

### 10.10 不再"面板没拉完就退出"（2.9.5）

原来是固定 120ms 后 `stopOneHanded()`。面板展开动画要 300~400ms，
等于动画走到三分之一窗口就开始上移，观感是"面板被甩走 / 还没拉出来就缩回去了"。

改成两段式：

```
armExit(why)          记录"想退"，挂 520ms 超时兜底
onShadeSettled(why)   面板状态切换（StatusBarStateControllerImpl#setState）时回调
doExit()              真正 stopOneHanded()
```

- 落定信号到了也要等满 **380ms**（`EXIT_MIN_SETTLE_MS`）再退，覆盖动画长度；
- 落定信号没来（MIUI 这条路径实测不调 `setState`）就 520ms 超时兜底；
- pending 期间重复的展开信号直接忽略，不会把超时不断往后推。

实测：`cmd statusbar expand-settings` → expand 到 stop 间隔 527ms，
控制中心完整铺开、背景已归位（截图核对）。
