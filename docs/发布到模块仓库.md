# 发布到 LSPosed 官方模块仓库

LSPosed / Vector 管理器里的"可下载模块列表"来自 GitHub 组织
[`Xposed-Modules-Repo`](https://github.com/Xposed-Modules-Repo)：一个模块一个仓库，
仓库里只放 release，不放源码。

## 收录要求

官方写在 [`Xposed-Modules-Repo/.github`](https://github.com/Xposed-Modules-Repo/.github) 里，四条硬性条件：

| # | 要求 | 本模块对应 |
|---|---|---|
| 1 | 仓库名 = 模块包名 | `io.github.zpan2327.hyperhand` |
| 2 | 仓库 description 非空，作为模块显示名 | `HyperHand` |
| 3 | 至少一个 release | 见下文 tag 规则 |
| 4 | release 至少有一个 `.apk` 资源，且 tag 必须是 `VersionCode-VersionName` | `20000-2.0.0` |

tag 里用短横线，不是 `v2.0.0`。机器人只会**修正**写错的 tag，不会替你补 APK；
而且"只编辑 release 资源、不改 release 内容"不会触发机器人，必须动一次 release 本身。

## 签名密钥（3.3.0 起随仓库保存）

`module/signing/hyperhand.keystore` 已提交进仓库，别名 `hyperhand`，口令见
`module/build.gradle.kts` 的 `KEYSTORE_PASS` 默认值。**换机器 / 重装系统后不要再让
构建脚本生成新密钥**——签名一变，用户就只能先卸载旧版再装，也会和模块仓库里的
历史版本不同签名。`module/out/` 仍然忽略，但 keystore 本身必须留在版本库里。

**`debug` / `fast` / `release` 三个变体都用这把钥匙**（`buildTypes` 里显式指定
`signingConfig = signingConfigs.getByName("hyperhand")`）。早先 `fast` 曾签机器的
`~/.android/debug.keystore`，于是「fast 能覆盖 debug、覆盖不了 release」，反过来也一样，
两次都撞上 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。**不要再让任何变体退回 debug 钥匙。**

校验任一变体：

```bash
apksigner verify --print-certs module/build/outputs/apk/fast/module-fast.apk | grep SHA-256
# 期望 912fa6bf9a4611ddf4d0b12437c8b2e03681cc7e00e22b36c3f7b4889f276a7a
```

已装过 debug 签名包的机器要迁移到正式签名（规则不丢，模拟器验证过）：

```bash
su -c 'cp -r /data/data/io.github.zpan2327.hyperhand/shared_prefs/. /sdcard/hhprefs/'
adb uninstall io.github.zpan2327.hyperhand
adb install module/build/outputs/apk/fast/module-fast.apk
# 卸载重装后 uid 会变，先读新的再恢复：
UID=$(adb shell "dumpsys package io.github.zpan2327.hyperhand | grep -m1 userId=" | grep -oE 'u0_a[0-9]+')
su -c "mkdir -p /data/data/io.github.zpan2327.hyperhand/shared_prefs && \
  cp /sdcard/hhprefs/*.xml /data/data/io.github.zpan2327.hyperhand/shared_prefs/ && \
  chown -R $UID:$UID /data/data/io.github.zpan2327.hyperhand && \
  chmod 771 /data/data/io.github.zpan2327.hyperhand{,/shared_prefs} && \
  chmod 660 /data/data/io.github.zpan2327.hyperhand/shared_prefs/*.xml && \
  restorecon -R /data/data/io.github.zpan2327.hyperhand"
```

LSPosed 里的「模块启用」与「作用域」随卸载丢失，需要重新勾一次。

### 必须保持一致的「三处密钥」

当前正式签名指纹（SHA-256）：

```
91:2F:A6:BF:9A:46:11:DD:F4:D0:B1:24:37:C8:B2:E0:36:81:CC:7E:00:E2:2B:36:C3:F7:B4:88:9F:27:6A:7A
```

发布链路上有三处持有这把密钥，**任何一处漂移都会让 release 的 APK 和用户已装版本
签名对不上**：

| 处 | 位置 | 由谁使用 |
|---|---|---|
| ① 本地 / 仓库文件 | `module/signing/hyperhand.keystore`（已提交） | 本地构建 |
| ② GitHub Secret | 源码仓库的 `ANDROID_KEYSTORE_B64`（keystore 的 base64） | CI 构建时恢复 |
| ③ CI 恢复结果 | workflow `Restore signing key` 步骤写回 `module/signing/` | CI 构建实际使用 |

正常状态：① = ② = ③ = 上面那把指纹。CI 的 `Restore signing key` 步骤会用 ②
**覆盖** ①（checkout 出来的那份），所以**真正决定 CI 签名的是 Secret ②**：

```yaml
- name: Restore signing key (optional)
  env:
    KEYSTORE_B64: ${{ secrets.ANDROID_KEYSTORE_B64 }}
  run: |
    mkdir -p module/signing
    if [ -n "${KEYSTORE_B64:-}" ]; then
      printf '%s' "$KEYSTORE_B64" | base64 -d > module/signing/hyperhand.keystore
    else
      echo "未配置 ANDROID_KEYSTORE_B64，本次使用临时签名密钥"
    fi
```

因此：

- ** Secret ② 必须与仓库文件 ① 是同一把**。Secret 一旦缺失或过期，CI 会走 `else`
  分支生成一个临时 keystore（主题 DN 相同、公钥不同），编译出的 APK 签名就变了。
- **换密钥要三处一起换**：先更新 ① 并提交，再把新的 keystore base64 写进 ②，
  ③ 是 CI 自动恢复的、不用手动动。只换其中一处必然不一致。
- **备份**：`research/hyperhand_signing/HyperHand-签名密钥.zip` 含 keystore、
  证书 pem 与签名信息（别名 / 密码 / 指纹），跨机器时从这里取。

#### 更新 Secret 的方法

Secret 不能明文写，要用仓库公钥做 NaCl sealed box 加密后再 PUT。步骤：

1. `pip install pynacl`；
2. 读 `module/signing/hyperhand.keystore` 的字节，`base64.b64encode` 得到文本 `b64`；
3. `GET /repos/zPan2327/HyperHand/actions/secrets/public-key`，拿 `key_id` 和公钥（base64）；
4. `SealedBox(PublicKey(base64.b64decode(公钥))).encrypt(b64.encode())`，再 base64 得 `encrypted_value`；
5. `PUT /repos/zPan2327/HyperHand/actions/secrets/ANDROID_KEYSTORE_B64`，
   body 为 `{"encrypted_value":"<第 4 步的密文>","key_id":"<key_id>"}`，
   header 带 `Authorization: Bearer <PAT>` 与 `X-GitHub-Api-Version: 2022-11-28`。

PUT 对已存在的 Secret 是更新；header 的 API 版本别省，否则可能返回 401。密钥明文
只在本地出现，传上去的是密文。改完可用一次 tag 构建验证：比对 release APK 的
签名指纹是否仍为上面那串。`apksigner verify --print-certs xxx.apk | grep -i sha-256`。

### 发版只走一条路径（重要）

**绝不要「本地脚本上传 APK」和「CI 自动发布」同时进行。** 两者都写同一个 release，
后写的会删除并覆盖先写的资产（日志里是 `Deleting previously uploaded asset`），
一旦两边用的密钥不同，仓库里的 APK 就会变成另一把签名，用户覆盖安装时报签名冲突。

- **推荐：只走 CI** —— 见下文「每次发版」，打 `v*` tag 让 CI 构建并同步两个仓库，
  不要再跑本地 `publish_*.py` 上传 APK。
- 若必须本地脚本补发（如 beta、CI 故障），则**不要同时打 tag 触发 CI**，二选一；
  且本地构建用的 keystore 必须与 Secret ② 是同一把。
- 排查这类问题：比对三方指纹（本地 / 仓库 release / 用户已装），并看 CI run 日志里
  `Restore signing key` 打印的是「使用仓库 secret」还是「临时签名密钥」，以及
  `Deleting previously uploaded asset` 是否发生。

## 一次性准备

1. **提交仓库**

   打开 <https://modules.lsposed.org/submission>，用 GitHub 账号登录，填包名 `io.github.zpan2327.hyperhand`。
   机器人会在组织下建好同名仓库，并把你加成该仓库的 admin。

2. **配一个能写这个仓库的 token**

   GitHub → Settings → Developer settings → **Personal access tokens (classic)** →
   Generate new token，勾 `repo`（或细粒度 token 只给 `Xposed-Modules-Repo/io.github.zpan2327.hyperhand`
   的 `Contents: Read and write`）。

   然后在本仓库（源码仓库，不是模块仓库）→ Settings → Secrets and variables → Actions →
   New repository secret，名字填 `MODULE_REPO_TOKEN`，值粘贴 token。

   没配这个 secret 时，CI 的同步步骤会自动跳过，不影响本仓库的 Release。

## 每次发版

> 前置：确认上面「三处密钥」一致，且**本次只走 CI 这一条发布路径**——不要在打 tag
> 的同时用本地脚本上传 APK，否则会竞态覆盖。版本号在 `module/build.gradle.kts`
> 的 `defaultVersionName` / `minVersionCode` 里 bump，并同步更新 `CHANGELOG.md`。

```bash
git tag -a v2.0.0 -m "v2.0.0"
git push origin v2.0.0
```

CI 会做三件事：

1. 构建 `module/out/HyperHand.apk`，并用 `aapt2 dump badging` 读出真实的 `versionCode` / `versionName`；
2. 在本仓库发 Release（tag `v2.0.0`，附 APK，beta 自动标 prerelease）；
3. 把同一个 APK 同步到 `Xposed-Modules-Repo/io.github.zpan2327.hyperhand`，
   tag 用 `版本号-版本名`（如 `20000-2.0.0`）。

> **beta 版本不会自动同步**：workflow 的同步步骤带
> `!contains(steps.apk.outputs.version_name, 'beta')` 判据，避免测试版顶掉
> 管理器里的正式版。所以 `3.0.3-beta.N` 这类版本仍需按下面的「手动补发」发布到模块仓库；
> 源码仓库的 prerelease 仍由 CI 自动创建。

> **正式版（`3.1.0` 这类不含 beta 的版本）**：同步判据通过，CI 会自动发布到模块仓库，
> 且源码仓库 Release 是 `prerelease: false` + `make_latest: true`。只有同步步骤被跳过
> 或失败时才需要手动补发，此时 `prerelease` 必须填 **`false`**（正式版），
> `name` 用 `HyperHand <版本名>`，不要带任何副标题。
> 模块显示名取**模块仓库的 description**（当前为 `HyperHand`），APK 的
> `android:label` 也必须一致。

## 手动补发（beta / CI 同步失败时）

用有模块仓库写权限的 PAT 调 API，`tag_name` 必须是 `versionCode-versionName`（如
`29906-3.0.3-beta.2`），`prerelease: true`，然后上传同名 APK 资源：

```bash
# 1) 建 release
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"tag_name":"29906-3.0.3-beta.2","name":"3.0.3-beta.2","prerelease":true}' \
  https://api.github.com/repos/Xposed-Modules-Repo/io.github.zpan2327.hyperhand/releases

# 2) 传 APK（release_id 取自上一步响应；Content-Type 不能省）
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/vnd.android.package-archive" \
  --data-binary @module/out/HyperHand.apk \
  "https://uploads.github.com/repos/Xposed-Modules-Repo/io.github.zpan2327.hyperhand/releases/$RELEASE_ID/assets?name=HyperHand.apk"
```

Windows 上 `curl` 是原生程序而 Python 读的是 MSYS 的 `/tmp`，两者路径不互通；
解析响应请走管道（`curl ... | python -c ...`），不要用 `curl -o /tmp/x.json` 再读。

对应的 workflow 片段：

```yaml
      - name: Publish to Xposed-Modules-Repo
        if: startsWith(github.ref, 'refs/tags/v') && env.MODULE_REPO_TOKEN != ''
        uses: softprops/action-gh-release@v2
        with:
          repository: Xposed-Modules-Repo/io.github.zpan2327.hyperhand
          token: ${{ env.MODULE_REPO_TOKEN }}
          tag_name: ${{ steps.apk.outputs.version_code }}-${{ steps.apk.outputs.version_name }}
          files: module/out/HyperHand.apk
```

```bash
# 模块仓库里是否已经有这次发布
curl -s https://api.github.com/repos/Xposed-Modules-Repo/io.github.zpan2327.hyperhand/releases/latest \
  | grep -E '"(tag_name|name|browser_download_url)"'

# APK 里的版本号（应与 tag 前段一致）
aapt2 dump badging module/out/HyperHand.apk | head -1
```

## 排错

| 现象 | 原因 |
|---|---|
| 管理器里搜不到模块 | 模块仓库的 latest release 还没有 APK，或 tag 不是 `版本号-版本名` |
| 同步步骤被跳过 | 没配 `MODULE_REPO_TOKEN`，或 token 对该仓库没有写权限 |
| 同步报 404 | 仓库还没通过 <https://modules.lsposed.org/submission> 创建出来 |
| 管理器里模块显示"需要更新的框架" | 框架实现低于 API 102（`module.prop` 里 `minApiVersion=102`）；换 Vector 2.x / 新版 LSPosed |
| 模块启用后不生效 | 静态作用域只有 `com.android.systemui` + `com.miui.home`，改钩别的进程需要先改 `scope.list` 再发版 |
