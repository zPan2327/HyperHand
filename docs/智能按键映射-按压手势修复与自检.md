# 智能按键映射：按压手势修复与全组合自检

> 2026-11-25。用户反馈「双击和长按似乎用不了」，要求用模拟器把所有按压方式与动作的
> 排列组合验证一遍。本文记录根因、修法、自检方式与结论。

## 1. 症状

- 短按能用（音量键一按就执行映射的动作）。
- **长按几乎不触发**（按住 1 秒也不出动作）。
- **双击不灵**：要么第一下就先把短按动作执行了，要么连按三下之后每次单击都触发双击。
- 「保持原功能」形同虚设：映射成 `pass_through` 的键被吞掉，音量都不调了。
- 「播放 / 播放暂停」永远没反应（只暂停过、恢复不了）。

## 2. 根因

### 2.1 长按：等一个永远不会来的事件

旧实现靠 `interceptKeyBeforeQueueing` 里的 `ACTION_DOWN && repeatCount > 0` 判长按。
但 **repeat 事件是 `InputDispatcher` 内部合成的**（`processKeyRepeatLocked`），
只经过 `interceptKeyBeforeDispatching`，**不会再次进入 `interceptKeyBeforeQueueing`**。
也就是说 `onRepeat()` 是死代码，长按永远等不到触发条件。

修法：DOWN 时自己起定时器（`longPressMs`，来自映射参数），到点直接出 LONG；
若某些 ROM 真的送来 repeat，则要求「已按住 ≥ longPressMs」才认，作为兜底且只出一次。

### 2.2 双击：第一下先把短按执行了

旧实现在 DOWN 时对 `SHORT` 立即触发（`shortMap != null && longMap == null`）。
双击的第一下正好命中这条，于是「短按动作 + 双击动作」连着出，用户读到的是「双击不灵」。
另外 `tapCount` 触发后从不清零，连按三下之后每次单击都会立刻再触发一次双击。

修法：
- 只要同一个键上还配了双击 / 连按，短按就**推迟到多击窗口关闭后**再判定；
  只有「唯一映射」时才在 DOWN 立即触发，保持零延迟。
- 双击 / 连按触发后 `tapCount` 立刻清零，下一次按重新计数。
- 多击窗口用映射自己的 `doubleTapMs`（连按用一个略宽松的窗口）。

### 2.3 「保持原功能」吞键

旧代码对所有命中规则的事件一律 `return 0`，`pass_through` 只是"不下发动作"，
于是键被吞了、音量也不动 —— 新建规则默认就是 `pass_through`，表现就是「键坏了」。

修法：
- 四种按压映射**全是** `pass_through` → 完全不接管，事件透传给系统（音量正常）。
- 部分按压是 `pass_through`（例如短按=保持原功能、长按=下一首）：DOWN 必须吞掉
  （否则按住时音量会一路涨），松手后若最终该走系统音量，用
  `AudioManager.adjustStreamVolume(STREAM_MUSIC, …, FLAG_SHOW_UI)` **补一次**。

### 2.4 播放 / 播放暂停选不到会话

`MediaActions.pick()` 只接受 `STATE_PLAYING` 的会话。暂停中的会话被跳过，于是：
`play` 永远找不到目标、`play_pause` 永远只会"暂停"。

修法：按动作给出候选顺序 —— 正在播放 → 暂停中 → 其它活动状态；
包名限定时仍然严格（限定包里没有会话就直接放弃，绝不误控其它应用）。

## 3. 新状态机（`SkEngine`）

- 时间源抽象成 `Clock`（生产 = 独立 `HandlerThread`，自检 = 虚拟时钟）。
  动作统一走 `ActionSink`（生产 = `MediaActions`，自检 = 记录器），
  事件处理只回答「这个原始事件要不要吞」。
- 一次按压的状态：`active`（已接管）/ `fired`（已出过动作）/ `tapCount` /
  `downAt` / `lastUpAt` / 四个 press 的映射 / 长按定时器 / 多击窗口关闭定时器。
- 时序：

| 事件 | 行为 |
|---|---|
| DOWN(repeat=0) | 匹配规则 → 全 pass 则透传；否则取消上一轮定时器、累加 `tapCount`；连按/双击达成即出动作并清零；否则起长按定时器；唯一映射的短按立即出动作；**吞键** |
| 长按定时器 | 未出过动作 → 出 LONG |
| repeat>0 | 兜底：已按住 ≥ `longPressMs` 才出 LONG（只一次），否则继续等定时器 |
| UP | 取消长按定时器；未出过动作时：有多击映射 → 起窗口关闭定时器；否则出 SHORT；短按是 `pass_through` → 补一次系统音量；**吞键** |
| 窗口关闭 | 未出过动作 → 出 SHORT（或补音量），`tapCount` 清零 |

同键**同时**配双击与连按时：先达成的次数赢 —— 第 2 下双击就命中并清零，
所以 `repeatCount ≥ 3` 在这种组合下不可达。这条写进规范，不要当成 bug。

## 4. 自检（79 例，模拟器上跑）

入口（无界面，跑完自关）：

```bash
adb install -r module-fast.apk
adb shell am start -n io.github.zpan2327.hyperhand/.smartkey.SkSelfTestActivity
adb logcat -s HHSKTest
```

覆盖内容：

| 组 | 用例数 | 内容 |
|---|---|---|
| 单映射矩阵 | 48 | 2 键 × 4 按压 × 6 动作（下一首/上一首/播放/暂停/播放暂停/保持原功能） |
| 组合 | 17 | 短+长、短+双击、双+连按、四种全开、双击后第三次单击、pass 与长按混配、只配长按的轻点 |
| 时序边界 | 9 | 双击窗口 300/600ms 的 ±20%、长按 500/1200ms 的 ±10%、连按 2 次、repeat 兜底 |
| 规则层 | 5 | 优先级、停用规则、总开关、键未映射、双键互不串扰 |

结论：**79/79 PASS**（Android 15 模拟器 Pixel_4_API_35，07:41 版本）。

自检跑的是生产用的 `SkEngine`，只是把时间源换成虚拟时钟，
所以不用 LSPosed、也不用真按键，毫秒内跑完且完全确定。

## 5. 已知取舍

- 只配「长按」一个映射时，轻点由 `adjustStreamVolume` 补偿音量（会弹系统音量条）。
- 只配「双击」时，第一下按下去没有任何反馈（要等窗口关闭才能确定不是双击），也不调音量。
- 消费掉 DOWN 后系统不会再产生 repeat，所以长按必须靠自己的定时器（§2.1）。
- 媒体动作的**实际效果**（真的切歌/暂停）只能在真机 system_server 里验；
  模拟器自检覆盖的是「哪个手势选出哪个动作」，以及会话选择的候选顺序。
