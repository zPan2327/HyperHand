### 0.1 已验证的关键事实（与原方案的差异）

1. **会话起点改用 `ShortcutMenuLayer.showShortcutMenu(IDragObject)`**，而不是 `com.miui.home.launcher.shortcuts.ShortcutMenu.showShortcutMenu`。后者在这版里**不存在**；`ShortcutMenu` 的显示方法是 `show([FZ[IIZ)` / `showWithAnim(ShortcutMenuPositionInfo)`。
2. **真正的触摸根是 `com.miui.home.launcher.SuperDraglayer`**（`DragLayer` 的父类，`BaseDragLayer` 的子类），`dispatchTouchEvent` / `onInterceptTouchEvent` 都在这里实现。原方案写 `DragLayer.dispatchTouchEvent` 也能钩到（Hook 封装会遍历父类），但应直接钩 `SuperDraglayer`。
3. **系统已有两个取消信号接口**：`com.miui.home.dragdrop.ShortcutMenuDragListener.onDragOverThresholdWhenShortcutMenuShowing(IDragObject)` 与 `onSecondaryPointerDownWhenShortcutMenuShowing(IDragObject)`，实现者是 `com.miui.home.launcher.touch.ItemLongClickListener$2`。直接钩它们，比自己算阈值/多指更可靠。
4. **`handleMotionEventWhenShortcutMenuShowing(MotionEvent)Z`（private）** 在 `isInShortcutMenuState()` 且动作为 DOWN/CANCEL 时，调用 `BaseLauncher.cancelShortcutMenu(7, new CancelShortcutMenuReason("click_outside_of_menu"))` 并 **return true（消费事件）**。这是「菜单显示时点外面会关菜单」的实现；**本次手势自己的 UP/MOVE 不走这个分支**，所以滑选路径不会被它吞掉。
5. **点击提交可以极简**：`ShortcutMenuItem.getOnClickListener()Landroid/view/View$OnClickListener;` 是 public abstract；`IconAndTitleShortcutMenuItemContainer.bindShortcutMenuItem(ShortcutMenuItem, ItemInfo)` 把它包成 lambda 设给 View，lambda 内依次 `OnClickListener.onClick(v)` → `ItemInfo.onLaunch()` → 收键盘。所以**直接 `itemView.performClick()` 就是原生点击的完整等价路径**，不需要反射 `View.mOnClickListener`。
6. **菜单项的命中判定与系统一致**：`IconAndTitleShortcutMenuItemContainer.isTouchPointInView(int,int)` 内部就是 `getGlobalVisibleRect(rect)` + `rect.contains(x,y)`。我们的外扩/滞回可以在这之上做。
7. **`mAppPersonaliseShortcutMenu` 在这版不存在**；实际字段是 `mAppShortcutMenu`、`mSystemShortcutMenu`、`mFolderShortcutMenu`、`mAddWidgetShortcutMenu`、`mWidgetShortcutMenu`、`mContentView`、`mBindedItemInfo`。
8. **取消原因/编辑状态类换了包**：`com.miui.home.state.api.CancelShortcutMenuReason`、`com.miui.home.state.api.EditStateChangeReason`；不再是旧文的 `com.miui.home.launcher.shortcuts.CancelShortcutMenuReason`。
9. **没有发现原生的「拖到项上抬手触发」**：`ShortcutMenuLayer.onDragEnd(IDragObject)` 只打日志/埋点（`trackShowingShortcutMenuWhenDropIcon`），不派发 item 点击。因此「二次触发」在本版风险很低，但仍保留 guard 以兼容旧版。
10. 这版引入 `com.miui.home.shortcutmenu.api.IShortcutMenu`、`com.miui.home.temp.ShortcutMenu`、`ShortcutMenuManager`、`ShortcutMenuPositionInfo` 等新类（R8 混淆明显，`$r8$lambda$…` 遍布）；**跨版本必须能力探测，不能硬编码单一路径**。

### 0.3 动态验证（Frida Hook + 真实手势，2026-11-18 root 后补测）

工具与证据：`research/hook_probe.js`（9 个 hook）、`research/hook_probe_bundled.js`（esbuild 产物）、`research/run_probe.py` / `run_probe2.py`（手势驱动）、`research/probe_log.txt` / `probe_log2.txt`（时序日志）、`research/menu2.xml`（uiautomator 菜单控件树）。

**(a) 菜单真实 View 结构（uiautomator dump，长按「设置」弹出）**

```
shortcut_layout [FrameLayout]
└─ shortcut_menu [LinearLayout]
   └─ content_view [LinearLayout]
      ├─ system_shortcut_menu [LinearLayout]  ← 3 个系统项，横向
      │   └─ 每项: LinearLayout(id="") + item_icon(ImageView)         无 item_title
      ├─ transparent_space_app_system [View] ← 系统项与应用项之间的间隔
      └─ app_shortcut_menu [LinearLayout]    ← 应用快捷项，纵向
          └─ 每项: LinearLayout(id="") + item_icon + item_title(TextView)
```

- **item 根 View 是 `resource-id=""` 的匿名 `LinearLayout`**，不是 `IconAndTitleShortcutMenuItemContainer` 本身；后者是它内部的 icon+title 容器。⇒ 枚举 item 不能靠 resource-id，要靠 §5.1 的 ViewGroup 层级 + `getChildAt()`；点击也应设在 item 根 View（`performClick`）或其内部容器（承载 `bindShortcutMenuItem` 的 listener）。
- 系统项只有图标（如应用信息/卸载/小窗），**无文本节点**；命中矩形必须取 item 根 View 的 `getGlobalVisibleRect`，不能依赖 `item_title` 存在。
- 应用项实测：`显示与亮度`、`声音与触感`、`WLAN`，每项高 ≈153px @480dpi（≈51dp），宽 ≈611px，与 §5 的矩形方案一致。
- 菜单弹出位置在**图标上方**（图标 (459,1472) 时，菜单 `[369,628][980,1306]`），不同位置/边缘会重定位——再次印证必须逐帧 `getGlobalVisibleRect`，不能用固定偏移。

**(b) Frida 时序日志关键结论**

| 现象 | 日志证据 | 结论 |
|---|---|---|
| 抬手瞬间菜单仍存在 | `E1`：`UP inMenu=true` → 之后 `DRAG_END`、`ITEM_CLICK` | **`isInShortcutMenuState()` 在本次 UP 时为 true**，可在 UP 时安全提交 |
| `performClick` 路径有效 | `E1a`：`ITEM_CLICK title=?`（独立 tap 触发 lambda） | **item 的 OnClickListener 链路可用**，`performClick()` 等价原生点击被动态证实 |
| 超阈值会关菜单 | `E2`：DOWN→`MENU_SHOW`→小移 30px→`UP inMenu=true` 同刻 `cancelShortcutMenu flag=9 reason=drag_over_threshold`→`MENU_HIDE` | 即使是 30px 的小位移，**在 UP 瞬间系统也会判定 drag_over_threshold 并关菜单** |
| 滑向 item 会被中途取消 | `E3`：MOVE(600,1200) 后 ~570ms 即 `cancelShortcutMenu flag=9 reason=drag_over_threshold`，随后 `UP inMenu=false` | **手指从图标滑向菜单项的途中，系统会因超阈值提前关闭菜单**，等 UP 时 item 已不存在 |
| 取消时 flag=9 | 多处 `flag=9 reason=drag_over_threshold`；`flag=7 reason=event_back`（返回键） | 取消原因可用于区分「拖动取消」(9) 与「点外/返回」(7) |

| 🔴 超阈值的精确时机与位移（无 dump 干扰复核，`threshold_console.txt`） | 第 1 步 MOVE 到 (204,2000)（≈50px）时 `inMenu=true`；第 2 步到 (232,1958)（累计≈100px）**当场** `cancelShortcutMenu flag=9` → `MENU_HIDE`；此后 8 步到 item 全程 `inMenu=false` | **阈值≈100px（≈33dp）**，在 MOVE 中**实时触发**，不是 UP 时；菜单在手指到达 item 前约 8 步就已消失 |

**(c) 由此产生的关键策略调整（必须写进实现）**

> **原方案假设「菜单保持显示，滑到 item 上 UP 时命中提交」在本版不成立。** 真机上，手指带着 DragObject 从图标滑向菜单项的路径会被 `ItemLongClickListener$2.onDragOverThresholdWhenShortcutMenuShowing` → `BaseLauncher.cancelShortcutMenu(9, drag_over_threshold)` 在系统层直接取消，菜单在到达 item 前就消失。

实现必须二选一（建议 A 为主、B 为辅）：

- **策略 A（推荐）——拦截取消信号 + 保住菜单 + 阻止图标拖动 + 在 UP 命中提交**：Hook `ShortcutMenuDragListener.onDragOverThresholdWhenShortcutMenuShowing(IDragObject)`（before），当判定当前处于「本次长按滑选会话、且手指正朝菜单区域移动、且菜单 item 可见」时，**短路该回调**（`param.result`/直接 return，阻止 `goToState(NORMAL)` 关菜单），让菜单在滑动全过程中保持；到 UP 时按 §5 命中判定 + §6 用 `performClick()` 提交。**关键补充（无 dump 复核新增）**：短路取消还不够——实测取消后系统会把剩余手势解释为拖动排序并把图标挪走，因此还必须同时抑制 `DragController` 的图标拾取/落位（见 §6.2），否则滑选失败且桌面图标被改位。这会让「长按后拖动图标排序」与「滑向菜单」冲突，需用**方向/落点预判**区分——手指朝菜单所在方向（本版为图标上方）移动且接近菜单矩形才拦截；否则放行原生排序。
- **策略 B（兜底）——在超阈值取消发生前提交**：不拦截取消，而是 Hook `IconAndTitleShortcutMenuItemContainer.isTouchPointInView`/`dispatchTouchEvent` 或每帧在 `SuperDraglayer.dispatchTouchEvent` 的 MOVE 中检测「手指已进入某 item 矩形且滑动距离≥阈值」，**在 MOVE 阶段就锁定并高亮**，随后的 drag_over_threshold 取消一旦发生、且手指仍在该 item 上时立即提交。此路径提交点更早，能绕过「UP 时菜单已关」的问题，但要处理「进入 item 后又滑出」的撤销。

**两条策略都要求：Hook `cancelShortcutMenu(int, CancelShortcutMenuReason)` 记录 flag/reason，作为会话状态机的一等输入（flag=9 拖动取消、flag=7 点外/返回），而非把「菜单 hide」笼统当取消。**

## 1. 目标、交互契约与边界

### 1.1 保留的原有交互（绝不破坏）

1. 长按应用图标 → 菜单弹出 → **抬手**，菜单保持打开；
2. 之后**再次点击**菜单项 → 正常执行该项；
3. 长按后继续移动手指 → 仍然是原生**拖拽图标**（排序/移入文件夹），本次模块不得抢走；
4. 长按文件夹 / 小部件 → 行为完全不变。

### 1.2 新增交互

同一次连续触摸内：长按图标 → 菜单弹出 → **手指不离开屏幕** → 滑到某个快捷项 → **在该项上抬手** → 直接执行该项。

- 滑动过程中当前命中项**高亮**，离开该项或离开菜单立即取消高亮；
- 「长按后点击菜单项」与「长按滑选」是两条互斥路径：后者只在**同一次触摸**内成立，且抬手时必须落在有效项上。
- 滑选失败（离开菜单、`ACTION_CANCEL`、第二指按下、菜单被系统关闭）→ 不执行任何快捷项，回到原生行为。

### 1.3 明确不做

- 不重绘、不替换系统快捷菜单的视觉（外观 100% 原生，高亮优先复用系统 pressed 态）；
- 不修改 `/system`、不替换 APK，OTA 不受影响；
- 不拦截、不消费普通触摸，只在「菜单已由本次 DOWN 打开」的窗口内工作。

### 3.1 Hook 装配原则

- **能力探测优先于版本号**：用 `findClass(...) != null` + `hookMethods(...) > 0` 决定是否启用，不硬编码 MIUI 版本字符串；
- **名字匹配、忽略参数表**（`Hooks.hookMethods` 已如此实现）：`showShortcutMenu`、`hideShortcutMenu`、`onDragEnd` 在版本间参数会变，名字稳定；但**同名不同参**要小心（如 `getDragInfo()` vs `getDragInfo(int)`）；
- **鸭式判定 DragObject**：不依赖具体类，按「有 `getDragView()` / `getDragInfo*` 方法」识别；
- **多路径并存**：H1 与备胎、H4 与自算阈值同时装配，谁先命中用谁；不要因为一个失败就整体停用；
- **失败安全**：任何反射/调用异常都吞掉并写 debug 日志；**绝不**在 Hook 里抛异常到桌面进程；  
  |  |  |  |  
  | --- | --- | --- |
- **热路径零成本**：H3 的 `intercept` 第一行就是 `if (!cfg.slideEnabled || session == null) return PROCEED;`，未处于会话时只做一次引用比较。

## 4. 触控事件拦截与状态流转

### 4.1 为什么选 `SuperDraglayer.dispatchTouchEvent`

真机验证：`DragLayer` 只是薄壳，真正的 `dispatchTouchEvent` / `onInterceptTouchEvent` / `onTouchEvent` 都在父类 `com.miui.home.launcher.SuperDraglayer`（再往上才是 `BaseDragLayer`）。DOWN→MOVE→UP 全程可见，且能拿到 `getRawX/getRawY()`；菜单虽然画在 `ShortcutMenuLayer`，但手指事件仍由 DragLayer 层分发。Hook 在 `before` **只观察不改返回值**（`PROCEED`），因此原生拖拽、文件夹展开、图标排序都不受影响。

补充两点真机细节：

- `SuperDraglayer.onInterceptTouchEvent` 会调用 private `handleMotionEventWhenShortcutMenuShowing(ev)`：当 `BaseLauncher.isInShortcutMenuState()` 为 true 且动作是 **DOWN / CANCEL** 时，执行 `cancelShortcutMenu(7, new CancelShortcutMenuReason("click_outside_of_menu"))` 并 **return true 吞掉事件**。这是「菜单显示时点外面会关菜单」的原生逻辑；**本次手势自己的 UP / MOVE 不走该分支**，滑选不会被吞。
- `ShortcutMenuLayer.dispatchTouchEvent` 自己也会在 `mIsNeedSkipTouch=true` 时直接 return false（并打印 `don't dispatch touch because mIsNeedSkipTouch`）。所以**不要在菜单层观测触摸**，统一在 `SuperDraglayer` 观测。

### 4.2 状态机

```
                    ┌──────────────┐
                    │    IDLE      │  无本次手势；普通点击/长按/拖拽全走原生
                    └──────┬───────┘
                           │ DOWN 且 pointerCount==1（记 id/坐标/时间）
                           ▼
                    ┌──────────────┐
            ┌──────▶│   ARMED      │  等待菜单；MOVE 超 slop → CANCELLED（原生拖拽）
            │       └──────┬───────┘
            │              │ H1/H2 报告菜单已弹出（且本次 DOWN 未 CANCEL）
            │              ▼
            │       ┌──────────────┐
            │       │  MENU_OPEN   │  采 item 矩形（等动画结束）；逐帧 hit-test
            │       └──┬────────┬──┘
            │          │进入项    │离开全部项/离开菜单
            │          ▼         ▼
            │       ┌──────────────┐
            │       │  ITEM_HIT    │  高亮当前项；记录进入时刻、进入时的矩形
            │       └──┬────────┬──┘
            │          │UP 命中    │UP 未命中 / 第二指 / CANCEL / 菜单关闭
            │          ▼         ▼
            │       ┌────────┐ ┌──────────┐
            └───────┤COMMITTED│ │ CANCELLED │  清高亮，不再判定同一手势
                    └────────┘ └──────────┘
```

### 4.3 关键判定条件（防误触的核心）

提交（`COMMITTED`）必须**同时**满足：

1. **同源**：UP 的 pointerId == DOWN 时记录的主指 id；
2. **未提前取消**：`ARMED` 阶段位移未超 slop；全程未有 `ACTION_POINTER_DOWN` / `ACTION_CANCEL` / `hideShortcutMenu` / `reset` / 配置关闭 / 屏幕熄灭；
3. **菜单是这次 DOWN 打开的**：会话只在 H1/H2 触发时建立，且建立时 `session.down` 非空；菜单打开后再发生的点击（新的 DOWN）不会被跟踪 —— 这是「保留长按后点击」的关键；
4. **滑入而非“菜单在指下弹出”**：从 `MENU_OPEN` 起发生过一次**跨越 item 边界的进入事件**（`requireCross=1`），且累计滑动距离 ≥ `minSlideDp`（默认 10dp）；
5. **抬手仍在项内**：用**抬手瞬间重新采集**的矩形再判一次（菜单可能已滚动/动画），且命中项与高亮项一致（不一致则按未命中处理）；
6. 可选 `dwellMs`：进入项到抬手的停留时间 ≥ 阈值（默认 0，即 iOS 式“滑到就抬”也生效）。

> 若菜单弹出时手指恰好停在某项上，抬手不会触发：没有「进入事件」，累计位移也不够。这是最常见误触来源。

### 4.4 事件处理伪代码

```java
// H3：SuperDraglayer.dispatchTouchEvent —— before hook，只观察
Object intercept(Chain chain) {
    MotionEvent ev = (MotionEvent) chain.getArgs()[?];       // 按签名定位 MotionEvent 参数
    Cfg c = Cfg.get(app);
    if (!c.slideEnabled || (session == null && ev.getActionMasked() != ACTION_DOWN))
        return PROCEED;                                       // 热路径早退

    switch (ev.getActionMasked()) {
        case ACTION_DOWN:
            if (ev.getPointerCount() == 1 && session == null && isAppIconDownPossible(ev)) {
                session = new Session(ev.getPointerId(0), ev.getRawX(), ev.getRawY(),
                                      SystemClock.uptimeMillis());
                // 不消费，原生仍可识别长按
            }
            break;

        case ACTION_MOVE:
            if (session == null || session.cancelled || !session.menuOpen) break;
            int idx = ev.findPointerIndex(session.pointerId);
            if (idx < 0) { cancel(); break; }
            // 历史采样：API 34+ 用 getHistoricalRawX/Y；API 33 用 current raw 减当前 view 坐标
            // 得窗口偏移后加到 getHistoricalX/Y 上（一次手势内偏移恒定）
            for (sample : history(ev)) {
                session.addSample(sample.x, sample.y, sample.t);
                if (!session.entered && slideDistance(session) >= c.slideMinDp)
                    session.armedForCross = true;
                updateHit(sample.x, sample.y);                // §5
            }
            break;

        case ACTION_POINTER_DOWN:
            cancel();                                          // 多指：本次滑选作废，原生多指照常
            break;

        case ACTION_UP:
            if (session == null || session.cancelled) break;
            int up = ev.findPointerIndex(session.pointerId);
            if (up >= 0 && canCommit(ev.getRawX(up), ev.getRawY(up), c)) {
                commit(session.hitItem);                       // §6
            } else {
                clearHighlight();
            }
            finishSession();
            break;

        case ACTION_CANCEL:
            cancel();
            break;
    }
    return PROCEED;                                            // 永不消费事件
}
```

`isAppIconDownPossible()` 只在 DOWN 时做**廉价**判断（落点是否在工作区图标网格 / 是否 dock 区）；真正的应用图标确认放在 H1 的 `dragInfo` 上（类名含 `AppInfo`/`ShortcutInfo`、且 `!isInFolder()`），避免 DOWN 时做昂贵遍历。

## 5. 命中判定与高亮

### 5.1 采集 item 矩形

- 菜单打开后，从 H6 的五个 ViewGroup（`mAppShortcutMenu`、`mSystemShortcutMenu`、`mFolderShortcutMenu`、`mAddWidgetShortcutMenu`、`mWidgetShortcutMenu`；**本机没有 `mAppPersonaliseShortcutMenu` 和 `mArrow`**）遍历直接子 View；
- 过滤：`instanceof IconAndTitleShortcutMenuItemContainer && hasData()==true && getVisibility()==VISIBLE && isShown() && getAlpha()>0.1f`；
- 矩形：`View.getGlobalVisibleRect(rect)` + `rect.contains(rawX, rawY)` —— 与系统私有方法 `IconAndTitleShortcutMenuItemContainer.isTouchPointInView(int,int)` 完全一致（已反汇编确认），默认向外膨胀 `hitSlopDp`（默认 6dp）；
- **每次 MOVE 重新计算**，绝不缓存。原因：多项快捷方式时菜单可滚动、展开动画期间矩形在变、横竖屏切换会重排；
- 动画期间（H7 的 fade-in 未结束，或菜单 `getAlpha()<0.95`）**只跟踪不高亮**；H7 的 fade-out 回调或 100ms 兜底延迟后再开始正式采样。

### 5.2 滞回（hysteresis）

进出用不同阈值，避免边界抖动导致高亮闪烁：

- 进入：矩形外扩 `hitSlopDp`；
- 退出：命中后改用 `hitSlopDp - hysteresisDp`（默认 6−4=2dp）的内缩矩形；
- 只有手指**完全离开内缩矩形**才清除高亮；
- 手指离开「菜单整体包围盒 + 24dp」→ 记 `leftMenu=true`，清高亮；再次进入允许，但必须重新产生进入事件并满足 dwell（若配置）。

### 5.3 菜单滚动

- 菜单内含可滚动列表时，MOVE 的每帧重采矩形即可正确跟随滚动（§5.1）；
- 不默认做边缘自动滚动（会与原生 `RecyclerView`/`ScrollView` 抢手势）；`slideAutoscroll=1` 时才启用：手指距容器顶/底 ≤ `edgeDp`（默认 24dp）且容器是可滚动类时，按 `speed = k·(1 - d/edgeDp)` 调 `scrollBy(0, ±speed·dt)`，随后同帧重采矩形；
- 滚动惯性未停时（`View.getScrollY()` 仍在变）抬手：仍用抬手瞬间的最新矩形判定，符合“所见即所得”；
- 若系统菜单本身把拖拽图标识别为滚动（某些版本），优先让原生滚动：本模块的高亮在滚动期间保持但不提交，直到手指静止 ≥ 60ms 或再次产生明确进入事件。

### 5.4 高亮实现（不外自定义的 UI）

1. **首选**：`itemView.setPressed(true)`，复用系统 `state_list` / ripple —— 视觉 100% 与原菜单一致；
2. 若该类忽略 pressed 态：叠加一层 16dp squircle 描边，颜色取 HyperHand 强调色 `#3482FF`（浅）/ `#277AF7`（深），alpha 0.35，不遮文字；
3. 切换项时：旧项 `setPressed(wasPressedBefore)` 精确还原，避免污染原生状态；
4. 反馈：进入项瞬间下发一次触感，按 HyperHand 触感表走 `HapticFeedbackCompat → View.performHapticFeedback → VibrationEffect` 链，用 `TAP_LIGHT`（或 `MESH_LIGHT`），32ms 节流；提交用 `BUTTON_MIDDLE`；
5. 所有高亮状态存在 `session` 里，`cancel()` / `finishSession()` 必须无条件清干净。

## 6. 释放触发与原生双触发抑制

### 6.1 提交路径（分层回退）

在 H3 的 `ACTION_UP` **before** 钩子里完成提交（此时菜单/item 还活着）：

```
1. 先标记 session.committed = true、sSuppressDrop = DragObject 实例（见 6.2）
2. 【首选·真机已验证】itemView.performClick()
   bindShortcutMenuItem 把 ShortcutMenuItem.getOnClickListener() 包装成
   OnClickListener 设给了 View；performClick() 会依次执行：
     ShortcutMenuItem.getOnClickListener().onClick(v) → ItemInfo.onLaunch() → hideKeyboardAsync()
   与用户点击该项完全等价，无需反射 View.mOnClickListener。
3. 【备选】反射 ShortcutMenuItem.getOnClickListener() 后直接 onClick(itemView)
   —— 用于 View 的 listener 被某些版本清掉的情况；不会重复执行 onLaunch，
      必要时再调 ItemInfo.onLaunch()（按签名探测）。
4. 【最后手段】合成 ACTION_DOWN + ACTION_UP 调 itemView.dispatchTouchEvent()；
   风险最高，仅日志提示，不作为常规路径。
5. 调用一次 HapticFeedback（BUTTON_MIDDLE）
6. 写 oh_tuner_slide_last_hit（调试项：类名 + 文本 + 耗时 + 判定量）
7. return PROCEED —— 让原生继续完成 endDrag / 关菜单
```

> 关键：**不要**在 `after` 里做提交。原生 UP 处理很可能在 `chain.proceed()` 内结束拖拽并关闭菜单，`item` 已 detach，届时再点击会得到空上下文或无效状态。

### 6.2 抑制原生二次触发 + 阻止图标被拖动（本机双开低风险，但拖动必须抑制）

真机反汇编结论：`ShortcutMenuLayer.onDragEnd(IDragObject)` 只做 `ShortcutInfo` 包名的日志与 `AnalyticalDataCollector.trackShowingShortcutMenuWhenDropIcon()` 埋点，**不派发 item 点击**；也没有发现 `onDrop → itemView.performClick()` 的链路。因此本机**不会**出现原生与模块各触发一次的“双开”。

但**无 dump 复核发现一个必须处理的副作用**：菜单在 ~100px 处被 `drag_over_threshold` 关闭后，系统把剩余手势解释为拖动排序，TEST A 结束时图标从 `[36,1900][318,2185]` 被真正挪到了 `[318,1330][600,1615]`。所以策略 A 短路取消信号后，**还必须让这次手势彻底不走 drag**：

- 在 `SuperDraglayer.findActiveController(MotionEvent)` 或 `DragController.startDrag` 的 before 钩子里，当判定为滑选会话（手指朝菜单方向且菜单 item 可见）时，短路 drag 拾取——使这个手势期间 `DragController` 不接管手指、不产生可落位的 drag 状态；
- 若无法安全短路 `findActiveController`（它关系到所有拖拽），退而求其次：在 UP 之前调用 `BaseLauncher.resetDragItems()` + `DragView.remove()` 清掉 drag 状态，并在提交后确认图标 `ItemInfo` 的 cellX/cellY 未被改动（必要时记录会话开始时的 cell 并在取消时恢复）；
- 提交后仍需保证原生 `endDrag` 正常执行，不能让桌面卡在 dragging 态。

双开 guard（兼容旧版/其他机型）仍保留：

- 若探测到 `ShortcutMenuLayer` / `DragController` 存在 `onDrop`、`dispatchDropComplete` 等方法，钩其 `before`；`sSuppressDrop` 与本次 DragObject 身份一致时短路，但**不要清 drag 状态**（让原生继续 endDrag）；
- 退化方案：在提交路径外加一次性 guard，用 `session` 身份 + 短时间窗（直到本次 UP 分发结束）过滤第二次调用；窗口用 `Choreographer.postFrameCallback` 清除，**不用固定毫秒定时器**，避免误吞用户紧接着的第二次点击；
- `slideNativeFirst=1`（可选）：仅当动态确认原生存在「拖到项上抬手触发」时打开，本模块只做高亮与防误触，提交交给原生。

### 6.3 结束清理

- `finishSession()` / `cancel()`：清高亮、清 `sSuppressDrop`（在下一个 frame）、`session=null`、移除所有 item 强引用（只保留调试字符串）；
- DragView 残留：若 H6 短路后原生未 remove，调用 H9 的 `DragView.remove()` 一次（try/catch，重复 remove 无害）；
- 菜单关闭：不要主动调 `hideShortcutMenu`，让原生 endDrag 自己关，避免动画重入。

## 8. 边界场景处理矩阵

| 场景 | 处理 |
|---|---|
| 长按后抬手，再点菜单项 | 会话在抬手时 `finishSession()`；新的点击无会话 → 完全走原生 |
| 长按后拖动图标排序 | `ARMED` 阶段位移 > slop（默认 8dp）→ `CANCELLED`；原生拖拽不受影响 |
| 菜单在手指下方弹出，直接抬手 | 无「进入事件」+ 位移不足 → 不提交 |
| 滑出菜单再松手 | `leftMenu=true`，清高亮 → 不提交 |
| 滑出后重新滑回并松手 | 允许，但必须重新产生进入事件；`dwellMs` 可加严 |
| 手指在项边界抖动 | 滞回（进 6dp / 出 2dp）抑制闪烁；提交时以抬手瞬间矩形为准 |
| 菜单滚动中 | 每帧重采矩形；滚动期间不提交，静止 60ms 或新进入事件后才允许 |
| 第二指按下 | `ACTION_POINTER_DOWN` → 取消本次滑选；不改原生多指行为 |
| 系统手势/来电导致 `ACTION_CANCEL` | 取消，清高亮，不提交 |
| 菜单被系统关闭（`hideShortcutMenu` / `reset` / 切状态） | 取消提交；读 `CancelShortcutMenuReason` 写调试日志 |
| 按 Home / 切 App / 锁屏 | H8 的 `onPause` / `onStop` / 屏幕关闭 → 取消 |
| 快速连续两次长按 | `session` 在 UP/CANCEL 时清空；`sSuppressDrop` 下一个 frame 清，不串台 |
| 横竖屏切换 | 见 §9.2 |
| 文件夹 / 小部件长按 | H1 判定 `isInFolder()` 或非 AppInfo → 不建立会话 |
| 负一屏 / 最近任务里的长按 | `DragLayer` 不存在或 H1 未触发 → 不介入 |
| 抽屉内长按 | 只要 H1 触发就可用；若抽屉用不同 View 类，H3 兜底到 `Launcher.dispatchTouchEvent` |

## 9. 兼容性、风险与验证

### 9.1 不同小米桌面版本

- **本机（HyperOS 3 / 桌面 7.50.06.2581）已验证**：`com.miui.home.launcher.ShortcutMenuLayer`（`showShortcutMenu(IDragObject)`、`hideShortcutMenu(EditStateChangeReason)`、`mShortcutMenu` 字段）、`com.miui.home.launcher.SuperDraglayer`（真正的 `dispatchTouchEvent`）、`com.miui.home.launcher.shortcuts.ShortcutMenu`（五个菜单 ViewGroup，但**没有** `showShortcutMenu` / `mAppPersonaliseShortcutMenu` / `mArrow`）、`IconAndTitleShortcutMenuItemContainer`、`ShortcutMenuItem.getOnClickListener()`、`ShortcutMenuDragListener`、`com.miui.home.state.api.*`；
- **R8 混淆明显**（`$r8$lambda$…` 大量出现），但类名与方法名基本保留；字段重命名是主要风险（`mAppPersonaliseShortcutMenu`、`mArrow` 的消失就是证据）；
- 易变部分：`showShortcutMenu` 的归属（本机在 Layer，旧版在 `shortcuts.ShortcutMenu`）、`getDragInfo()` 有无 int 参数、`hideShortcutMenu` 的枚举包、`DragController` 的 drop 方法名 → **全部按方法名 + 参数个数匹配，不按签名硬编码**；
- 新版还出现 `com.miui.home.shortcutmenu.api.IShortcutMenu`、`com.miui.home.temp.ShortcutMenu`、`ShortcutMenuActivityScopeObjectProvider`，说明菜单逻辑仍在迁移中；H1 必须同时探测新旧两条路径；
- 全局版 ROM 包名 `com.mi.android.globallauncher`：HyperHand 静态作用域未包含，若需要支持，须在 `scope.list` 增加该包，并现场确认类名是否沿用 `com.miui.home.launcher.*`（**未验证，列为后续**）；
- 钩子失效时静默降级（日志 `class not found`），不会崩溃；与 HyperHand 现有策略一致。

### 9.2 横竖屏 / 折叠屏 / 多窗口

- 所有命中计算用 `getRawX/getRawY` 与 `getGlobalVisibleRect`（同为屏幕坐标），天然处理窗口偏移；
- 本机 `ShortcutMenuLayer` 自带 `isHomeAndDisplayRotationDiff(I)Z`、`isNotSupportDiffRotationTouch(I)Z`、`onDisplayRotationChanged(I)V`、`onScreenSizeChanged()V` —— **优先钩 `onDisplayRotationChanged`，立即 `cancel()`**；`Application/Launcher.onConfigurationChanged` 只作兜底；旋转后菜单 View 全部失效，下一次长按重新建立会话；
- 会话对象只持有 `WeakReference<View>`；`DragObject` / `DragView` 为强引用但生命周期严格限制在单次手势；
- 折叠屏/平板：`isPad` 分支的 item 数量与菜单布局不同（`getMaxShortcutItemCount` 在 pad 上被改过），枚举逻辑基于实际 View 树而非固定行列数，因此天然适配；但仍列为**未实机验证**风险。

### 9.3 性能与稳定性风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| H3 钩在每次触摸的热路径 | 中 | 会话外早退（一次引用比较）；历史采样只在会话内遍历；不在 MOVE 里做反射解析 |
| 每帧遍历 item + `getGlobalVisibleRect` | 低 | item 数量通常 ≤ 8；可在 `MENU_OPEN` 时缓存 item 列表引用，仅重算矩形 |
| 原生 drop 二次触发 | 低（本机已验证不触发）/ 中（跨版本） | 轻量 guard + `nativeFirst` 兜底；见 §6.2 |
| 高亮状态污染原生 pressed | 中 | 记录并还原原始 pressed；会话结束无条件清理 |
| `performClick()` 在无 listener 的项上无效 | 低 | `ShortcutMenuItem.getOnClickListener()` 备选；`hasData()` 过滤空项 |
| 菜单动画期间采到中间坐标 | 中 | H11 动画结束/100ms 兜底前不高亮、不提交 |
| 系统升级后菜单逻辑迁移（已出现 `temp.ShortcutMenu` / `IShortcutMenu`） | 中高 | 新旧双路径能力探测；静默降级；不修改系统文件，OTA 安全 |
| 🔴 滑向 item 途中被 `drag_over_threshold` 关菜单（动态证实） | **高（功能成立前提）** | 策略 A：Hook `onDragOverThresholdWhenShortcutMenuShowing` 按方向/落点预判短路；配合取消 flag=9 作为状态输入；见 §0.3c |
| 短路超阈值回调后长按拖动排序失效 | 中 | 严格方向/落点预判：只有手指朝菜单矩形移动才短路；否则放行原生排序 |

## 12. 真机跑通与三个关键修复（2026-11-18，功能已验证）

首版代码装上后**完全无效**（长按滑动仍移动图标）。用 logcat + Frida 逐层定位，发现并修复了三个致命问题；修复后真机完整跑通 iOS 式滑选。

### 12.1 三个根因与修复

1. **装配被跳过**：`hookLauncher()` 回调时机 `Hooks.currentApplication()` 返回 null，代码直接 `skip`，整个 ShortcutSlide 没装。
   → 修复：改为 `installSlideLater(cl)` 延迟 300ms + 12 次重试拿 Context（照搬 `markAliveLater()` 的成熟模式）。Hook 装配只依赖 ClassLoader，不依赖 Context。
2. **拦截点选错**：原代码 Hook `ShortcutMenuDragListener.onDragOverThresholdWhenShortcutMenuShowing`（含实现类 `ItemLongClickListener$2`）。Frida 实测：真实取消路径上该回调**根本不被调用**，真正汇聚点是 `BaseLauncher.cancelShortcutMenu(int flag, reason)`（flag=9=drag_over_threshold，flag=7=点外部）。
   → 修复：改 Hook `BaseLauncher.cancelShortcutMenu`，在 flag==9 且滑向菜单时短路。
3. **反射遍历整体抛错**：`BaseLauncher.getDeclaredMethods()` 因同类里别的方法签名引用本 ROM 缺失类 `NewHomeView`，整体抛 `NoClassDefFoundError`，目标方法拿不到。
   → 修复：用 `getDeclaredMethod("cancelShortcutMenu", int.class, CancelShortcutMenuReason.class)` 精确取单个方法，绕开遍历。

附带的时序修复：`ACTION_CANCEL` 早于 flag=9 到达，原先立即清 state 导致阈值取消被放行 → 改为 ACTION_CANCEL 只标记不清理；提交瞬间立刻设 `guardUntil=600ms` 且 `COMMITTED` 态吞掉 flag=9，阻止 UP 后原生补发取消把图标落到滑选终点。

## 15. 放开后图标漂移 + 震动"嗡嗡"的修复（16:20）

### 15.1 放开后漂移：真机日志定位到 3 个时序 bug

用户反馈："长按滑动完放开之后，图标还是会漂移"。抓 `logcat` 发现一条决定性证据：

```
16:08:54.069  UP inSlide hitAt=225,1920 src=drag
16:08:54.071  DROP invoked in=(225,1920) state=0 down=174,2489   ← state 竟是 0(IDLE)！
16:08:54.071  DROP restore to down point (174,2489)
```

提交明明把 `state` 设成了 `COMMITTED(3)`，2ms 后 drop 里却是 `IDLE`。根因：**SuperDraglayer 会把同一手势的事件重复分发多次**（同一次手势的 `ACTION_CANCEL` 日志打了 5 发，修复后验证脚本里重复 `ACTION_UP` 打了 8 发）。链式反应：

1. 第 1 个 `ACTION_UP`：`state==SLIDING` → `commitOrAbort()` → `state=COMMITTED`、`restoreIconOnDrop=true`、`guardUntil=now+600`。
2. 第 2~8 个 `ACTION_UP`：`observe()` 的 `else` 分支无条件 `state=IDLE`，**把 COMMITTED 冲掉**（旧代码没排除这个状态）。
3. 状态变 IDLE 后，原生补发的 `flag=9` 在 `onCancelMenu`/`onThresholdSource` 里被判定为"无活动会话"→ `PROCEED` 放行 → 原生执行拖动落位 → **图标落到滑选终点（漂移）**。
4. 叠加问题：`drop` 里 `restoreIconOnDrop` 是"一次性消费"（第一个 drop 用完就置 false），若 `drop` 也被重复调用，后续 drop 用真实落点 `(inX,inY)` 落位，同样漂移。

### 15.2 三道保险（互不依赖 state）

| 保险 | 位置 | 做法 |
|---|---|---|
| A | `observe(ACTION_UP)` | `else if (state==COMMITTED)` 分支：只打日志、不改 state，保住提交态与 restore guard |
| B | `drop` hook | `restoreIconOnDrop && now<restoreIconUntil` 窗口内**每次 drop 都钉回原格**，不再一次性消费（靠 1.5s 超时失效） |
| C | `onCancelMenu` + `onThresholdSource` | flag=9 在 restore 窗口内**无条件吞掉**，不看 state；源头与汇聚点行为一致 |
| D | `cancel()` | 已从 `COMMITTED` 进入收尾时不清 `restoreIconOnDrop`（防 `performClick` 打开新页触发 flag=7 → cancel 清标志） |

坐标系已反编译核对：`isMoveOverShortcutMenuMoveThreshold(III)` 直接用 `mMotionDownX/Y` 与 handleMove 的 x/y 做 `hypot`，确认为同一 raw 屏幕坐标系，`pinCoords()` / `drop restore` 用它归位无误。

### 15.3 震动："嗡嗡"→ 短促强劲

`crispTick()` 原走 MIUI `BUTTON_SMALL` effect id，经 HapticFeedbackUtil 的衰减包络出来是软绵绵的"嗡嗡"。改为**绕过 MIUI 效果层**，直接命令线性马达：

- 首选 `VibrationEffect.startComposition().addPrimitive(PRIMITIVE_CLICK, 1f)`——强度拉满、时长由马达固件定（约 8~12ms），一记干净的"咔"，无拖尾。
- 兜底 API 26 `createOneShot(12, 255)` 极短满振幅（不再用长波形）。
- 节流用独立 id `0x43524950`，避免与 BUTTON_SMALL 共用节流槽。

### 15.4 验证

- 单次：`UP ignored (already COMMITTED, keep restore guard)` 连打 8 次（坐实重复 UP 根因）、`DROP invoked ... state=3`（不再被冲成 0）、`DROP restore to down point (177,2042) state=3`、网格 **完全一致**。
- 三轮连续：每轮 STABLE，PIN=3、COMMIT 正常。

## 18. "滑动不选后点图标不打开 App"的根因与修复（17:38，Frida 探测驱动）

### 18.1 用户反馈

### 18.2 Frida 探测：原生事件无法区分"点击"与"长按/滑动"

`research/probe_longpress.js` + `run_longpress.py`（关闭模块开关后探测原生行为）得到决定性结论：

| 场景（菜单开着时） | SuperDraglayer 事件 | 原生 performClick | 原生 startDrag |

| 长按图标(DOWN 700ms UP) | 仅 DOWN | ❌ | ❌ |

- 最初的 `menuShowing` 布尔判定不可靠：滑动 abort/cancel 路径会把它清成 false，但菜单物理仍开着 → 点击被吞、我的逻辑又不触发；

### 18.3 修复（ShortcutSlide.java）

1. **物理可见性兜底**：新增 `menuPhysicallyVisible()`（直接看菜单 item 是否还在屏幕上），判定条件从 `menuShowing` 改为 `menuShowing || menuPhysicallyVisible()`，跟着菜单真实状态走。
2. **区分点击与滑动靠 MOVE（唯一可靠信号）**：DOWN 命中图标后不立即打开，而是 arm 一个延迟任务；期间若有 MOVE（滑动）→ 立即取消。窗口 400ms（真人滑动 MOVE 在 50~300ms 内到达，能被取消；点击手指早已抬起，400ms 后打开无感知延迟）。
3. **消除重复 DOWN 导致的取消失效**：MIUI 会把同一手势的 DOWN 重复分发十几次。之前每次 DOWN `new Runnable + postDelayed`，`removeCallbacks` 只能删最后一个，旧任务残留会误触发。改为**单一复用 Runnable** + 100ms 时间去重（只有间隔>100ms 才算新手势、才重新 arm；重复 DOWN 不重置取消标志）。

延迟任务执行时同时校验 `!iconTapCancelled && iconTapSid==sessionId && state==IDLE`，任一不满足即放弃。

### 18.5 设计取舍

"菜单开着时长按图标不动"在原生 MIUI 本就无任何响应（探测证实），无实际用途，故不为它牺牲点击体验。真正要防的是"滑动被误判成点击"——由 MOVE 信号可靠覆盖。

## 19. 点击菜单项与底部图标冲突 / 补点按震动

### 19.1 现象（真机复现）

桌面第二页：长按「米家」→ **直接点**菜单里的「添加小部件」→ 小组件选择器弹出，同时打开了菜单下面压着的「Meta」（用户实测为 QQ）。同一次 DOWN 既被原生菜单处理，也分发到了 `SuperDraglayer`，被 §18 的"补点图标"逻辑当成点图标。

### 19.2 修复

- `observe()` 的 DOWN 分支在 arm「点图标打开 App」之前，先用 `isOnMenuItem(downX, downY)` 判断落点是否落在任一可见菜单项矩形内；是则 `cancelPendingIconTap()` 并直接退出，菜单项点击完全交给原生处理。
- `onMenuHidden()` **不能**调用 `cancelPendingIconTap()`：菜单开着点图标时原生也会先 hide 菜单，那样会把待执行的补点任务一起取消，导致点击失效（回归实测 armed 但无 performClick）。

### 19.3 补点按震动

`iconTapRunnable` 原先在 `performClick()` 后调用 `Haptics.clickPrimary()`，导致"滑选不选 → 点图标打开 App"也震动。已删除该调用（保留滑选命中菜单项 `commitOrAbort()` 中的震动）。

- 修复后：`armed=0`、`performClick=0`、`skipped=11`、TOP=`com.miui.personalassistant/.picker...PickerHomeActivity`（只弹小组件选择器）✓
